# 1. Що ми хотіли отримати

До цього моменту TechBaza вже мала фізичний напрямок системи:

- ESP32-S3;
- ізольований RS485;
- Modbus RTU;
- частотний перетворювач;
- майбутнє керування насосом;
- майбутній 4G-зв'язок;
- вебінтерфейс для клієнта, сервісу та адміністратора.

Але для повноцінного IoT-продукту потрібна серверна частина.

На цьому етапі ми не створювали ще сам backend і не підключали ESP32 до Інтернету. Ми підготували фундамент, на якому вони будуть працювати.

Головна ціль етапу:

```text
Підготувати середовище, у якому надалі будуть працювати:

ESP32
  ↕
MQTT
  ↕
Backend
  ↕
PostgreSQL
  ↕
Frontend
```

# 4. Навіщо нам Docker

Docker використовується як середовище запуску серверних компонентів.

Без Docker довелося б окремо встановлювати та конфігурувати:

- PostgreSQL;
- Mosquitto;
- Python backend;
- frontend;
- додаткові служби;
- залежності кожного сервісу.

Docker дозволяє запускати ці частини в ізольованих контейнерах.

Схематично:

```text
Windows
  │
  └── Docker Desktop
        │
        ├── PostgreSQL container
        ├── Mosquitto container
        ├── Backend container       ← буде пізніше
        └── Frontend container      ← буде пізніше
```

Перевага такого підходу: однакова структура може працювати спочатку на локальному комп'ютері, а потім на Linux-сервері.

# 6. PostgreSQL

## 6.1. Для чого він потрібен

PostgreSQL — це постійна база даних TechBaza.

У майбутньому вона буде зберігати:

- користувачів;
- організації;
- клієнтів;
- об'єкти;
- контролери;
- частотні перетворювачі;
- насоси;
- датчики;
- модулі;
- права доступу;
- телеметрію;
- аварії;
- команди;
- історію подій;
- журнал дій.

Приклад майбутньої структури:

```text
Клієнт
  │
  └── Об'єкт
        │
        ├── Контролер
        │     │
        │     ├── VFD
        │     ├── датчик тиску
        │     ├── датчик струму
        │     └── інші модулі
        │
        └── Історія
              ├── телеметрія
              ├── аварії
              └── команди
```

## 6.2. Порт

Стандартний порт PostgreSQL всередині контейнера:

```text
5432
```

На Windows порт 5432 виявився недоступним або зайнятим.

Тому ми змінили зовнішній локальний порт на:

```text
5433
```

Схема:

```text
Windows
127.0.0.1:5433
      │
      ▼
Docker container
PostgreSQL:5432
```

Це не змінює сам PostgreSQL. Усередині контейнера він продовжує працювати на стандартному порту 5432.

## 6.3. Перевірка роботи

Для прямого входу в PostgreSQL використано:

```powershell
docker exec -it techbaza-postgres psql -U techbaza -d techbaza
```

Після входу:

```text
techbaza=#
```

Перевірка версії:

```sql
SELECT version();
```

Отримано:

```text
PostgreSQL 16.15
```

Перевірка активної бази:

```sql
SELECT current_database();
```

Отримано:

```text
techbaza
```

Вихід:

```text
\q
```

Таким чином підтверджено, що PostgreSQL:

- стартує;
- відповідає;
- приймає SQL-запити;
- працює саме з базою `techbaza`.

Docker healthcheck також показав:

```text
techbaza-postgres  Up (healthy)
```

# 7. MQTT та Eclipse Mosquitto

## 7.1. Для чого потрібен MQTT

MQTT буде основним транспортом повідомлень між польовим контролером та сервером.

Приклад майбутньої телеметрії:

```text
ESP32
  │
  │ frequency = 42.5 Hz
  │ current = 18.3 A
  │ pressure = 4.2 bar
  │ state = running
  ▼
MQTT Broker
  ▼
Backend TechBaza
```

Команда у зворотний бік:

```text
Backend
  │
  │ START
  │ STOP
  │ SET_FREQUENCY = 45
  ▼
MQTT Broker
  ▼
ESP32
  ▼
RS485 / Modbus
  ▼
VFD
```

## 7.2. Що таке broker

Mosquitto не є контролером насоса і не є базою даних.

Він працює як центральний розподілювач повідомлень:

```text
Publisher
    │
    │ повідомлення
    ▼
 MQTT Broker
    │
    ▼
Subscriber
```

Той, хто надсилає повідомлення, називається publisher.

Той, хто слухає потрібний topic, називається subscriber.

---

# 8. Перша реальна MQTT-перевірка

Для тесту використано topic:

```text
techbaza/test
```

У першому терміналі запущено subscriber:

```powershell
docker exec -it techbaza-mosquitto mosquitto_sub -h localhost -t techbaza/test -v
```

Він почав очікувати повідомлення.

У другому терміналі виконано:

```powershell
docker exec -it techbaza-mosquitto mosquitto_pub -h localhost -t techbaza/test -m "hello from TechBaza"
```

Subscriber отримав:

```text
techbaza/test hello from TechBaza
```

Це підтверджує реальну передачу:

```text
mosquitto_pub
     │
     │ "hello from TechBaza"
     ▼
Eclipse Mosquitto
     │
     ▼
mosquitto_sub
```

Таким чином MQTT-брокер не просто запущений — він реально приймає, маршрутизує та передає повідомлення.

# 10. Поточна MQTT-безпека

Поточний Mosquitto налаштований для локальної розробки:

```text
allow_anonymous true
```

Це допустимо лише для локального тестового середовища.

Для production необхідно буде додати:

- TLS;
- окремі логіни / паролі або сертифікати пристроїв;
- ACL;
- розмежування topic-ів;
- заборону анонімних підключень;
- обмеження зовнішнього доступу.

Майбутня production-схема:

```text
ESP32
  │
  │ MQTT + TLS
  │ device credentials
  ▼
MQTT Broker
  │
  ├── перевірка пристрою
  ├── ACL
  └── дозволені topics
  ▼
Backend
```

# 11. Модульний принцип TechBaza

Ключове правило архітектури:

**TechBaza — не один фіксований комплект обладнання, а модульний конструктор.**

Приклад:

```text
Об'єкт №1
├── ESP32
├── VFD
├── датчик тиску
└── датчик струму

Об'єкт №2
├── ESP32
├── VFD
├── датчик тиску
├── датчик рівня
└── вузол добрив

Об'єкт №3
├── ESP32
└── VFD
```

Backend, база даних та frontend у майбутньому мають розуміти, що встановлено саме на конкретному об'єкті.

Тобто сайт не повинен показувати датчик рівня клієнту, якщо такого датчика фізично немає.

# 15. Наступний логічний крок

Наступним шаром має стати backend.

План:

```text
Frontend
   ↓
FastAPI Backend
   ↙          ↘
PostgreSQL    MQTT
                ↓
              ESP32
```

Перший мінімальний backend повинен:

1. запускатися;
2. мати endpoint `GET /health`;
3. підключатися до PostgreSQL;
4. підключатися до MQTT;
5. надалі приймати телеметрію та відправляти команди.
