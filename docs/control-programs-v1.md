# Таймер і програми частоти v1

Поточна реалізація: backend **0.42.0**, firmware V3 **0.4.0**, MQTT command envelope v2.
Таймер і етапи додано у 0.41.0/0.3.0. Міграція `20261001_0020` додає окремі
[календарні розклади](control-schedules-v1.md); семантика витримок не змінилася.
Стендові запуски таймера, п'яти етапів, F5 під час RUN і STOP на другому
етапі зафіксовано 01.10.2026 нижче. Повне приймання PROGRAM-01 ще відкрите;
попередні докази START/STOP та діагностики 0.2.2 не замінюють перевірок програм.

## Інтерфейс

Типово показано звичайні START, STOP і частоту. Усередині
**«Додаткові налаштування команди»**, поруч із TTL, є вибір:

| Режим | Поведінка |
|---|---|
| Звичайне керування | Наявні окремі команди без таймера роботи |
| За таймером | Одна частота та її тривалість; потім STOP |
| За етапами | Послідовні етапи частота/тривалість; після останнього STOP |

Після згортання налаштувань видно вибраний режим і сумарний час витримки.
Підтвердження показує весь план. STOP доступний незалежно від вибраного режиму.
Під час програми частоту не можна змінити окремою командою: спочатку STOP,
потім новий план або ручне керування.

F5 скидає незбережену чернетку форми, але не виконання. Сайт відновлює
етап/залишок із телеметрії контролера та не надсилає повторний START.
За `diagnostics.program.command_id` автоматично відкривається збережена
серверна команда з усіма частотами/тривалостями, якщо є `command.read`.
План доступний тільки для читання; редактор нового плану прихований на час
активного виконання. Посилання «Переглянути етапи роботи» повертає до
нього після перегляду STOP або іншого запису журналу. Без `command.read`
прогрес залишається видимим за `telemetry.read`, але GET деталей не виконується.
Дозволи й належність команди до пристрою/організації перевіряються як раніше.
Закриття вкладки не скасовує прийнятий план. Залишок показується на момент
останнього зразка; без свіжої телеметрії сайт не вигадує відлік чи завершення.

## Контракт і часові межі

Нова команда — `vfd.program.start`; capability — `vfd.program`.
Таймер передає той самий формат з одним етапом. Приклад payload, а не
рекомендація частот для довільного двигуна:

```json
{
  "version": 1,
  "steps": [
    {"frequency_hz": 40, "duration_seconds": 7200},
    {"frequency_hz": 50, "duration_seconds": 3600}
  ]
}
```

Це дві години після досягнення 40 Гц, потім перехід на 50 Гц, ще година
після досягнення 50 Гц і STOP. Перехід додається до часу витримки.

- Від 1 до 8 етапів, кожен від 10 с, сумарна витримка до 24 год.
- Частота строго більша за нуль, до двох десяткових знаків. Контракт допускає
  до 100 Гц, але API перевіряє **межі конкретного пристрою**, а драйвер SU600
  додатково обмежує до 50 Гц. Нульова частота не використовується замість STOP.
- TTL 5–300 с (типово 30 с) обмежує перше прийняття/початок RUN.
  Уже розпочаті етапи не закінчуються через TTL.
- Витримка починається після читання RUN та вихідної частоти в межах
  ±0,11 Гц від цілі. Відлік — 64-бітний монотонний час контролера;
  зміна UTC/NTP або F5 його не прискорює.
- Кожен перехід частоти має до 60 с на підтвердження. Фінальний STOP також
  має 60 с; якщо зупинку не підтверджено, успіх не повідомляється.
- Серверний строк очікування Result після ACK:
  `сума_витримок + (кількість_етапів + 1) × 60 + 120 секунд`.
  Повторний ACK не продовжує строк. Для звичайних команд збережено
  `COMMAND_RESULT_TIMEOUT_SECONDS` (типово 120 с).

Плавний розгін між цілями визначають чинні налаштування частотника.
Годинні ramp-профілі, циклічні програми та бібліотека шаблонів у v1 не реалізовані.
Календарний запуск — окремий режим [«За розкладом»](control-schedules-v1.md). Ступені «20 → 30 → 40 Гц по годині» вже
виражаються трьома етапами, але не є безперервною лінійною зміною частоти.

## Виконання, зупинка та відмови

Сервер передає весь план одним запитом через наявний MQTT v2. Контролер
зберігає intent до першого запису, встановлює початкову частоту, перевіряє
її та надсилає RUN один раз. Наступні етапи змінюють частоту локально.
Перед етапом перевіряється конфігурація VFD, під час виконання — стан,
ціль/вихідна частота й аварія. Flash не записується щосекунди.

| Подія | Результат |
|---|---|
| Усі етапи виконано, прочитано STOP/0 Гц | `succeeded`, `stop_confirmed=true`; причина `program_completed` |
| STOP користувача або DISARM | Решта етапів скасована; після підтвердження STOP — `failed`, `program_cancelled` |
| Втрата готовності мережі, RS485/VFD/profile/storage fault | Програма переривається, запитується STOP, місцевий допуск знімається |
| Перезапуск ESP32 | Продовження програми заборонене; незавершений intent вимагає перевірки STOP; `restart_during_execution` |
| Перехід не підтверджено за 60 с | STOP і `program_transition_timeout` після підтвердженої зупинки |
| STOP не підтверджено за 60 с | Локальний outcome `Unknown`, сервер зрештою `result_unknown`; місцевий допуск знято, повтори STOP тривають, етапи не відновлюються |
| Повтор того самого command/request ID | Збережена відповідь, без нового RUN чи повторного відліку |

Result містить `steps_completed`, `step_count`, `stop_confirmed`;
успішний Result також містить `frequency_hz`. Підтвердження — читання стану/0 Гц у VFD, не незалежний
датчик обертання вала. STOP із сайту залишається мережевою командою.
Свідоме скасування `program_cancelled` видно в журналі, але окремий alarm
«помилка команди» для нього не створюється.

Прийнята програма продовжується локально без відкритого браузера, проте
чинна V3-політика **зупинки при втраті зв'язку** збережена. Logout або
відкликання capability зупиняють майбутню доставку, а не вже прийнятий
план; для його припинення потрібен STOP. Продовження без мережі потребує
окремої погодженої політики й у цьому релізі не вмикається.
Перед вимкненням права/capability керування слід спочатку виконати STOP:
відкликання доступу саме по собі не є командою контролеру.

## Права, прогрес і сумісність

Запуск вимагає `command.execute`, прив'язки до організації/пристрою,
увімкнених `vfd.control` і `vfd.program`, коректного frequency profile,
свіжої телеметрії поточного boot, `program.ready=true` та зупиненого VFD.
Перевірки виконуються при POST і повторно перед доставкою; локальний
контролер повторює необхідні перевірки перед фізичною дією.
Читач із `telemetry.read` бачить прогрес без права керування.

Необов'язковий `diagnostics.program` має `version`, `ready`, `command_id`,
`state`, `step_index`, `step_count`, `target_frequency_hz`,
`remaining_seconds`, `reason`. Етапи нумеруються від 1; idle має нульові
індекси й null-поля. Відновлення після reboot може показати індекс 0,
оскільки жоден етап не поновлюється. `ready` означає місцевий допуск,
а не відсутність активної програми. Застосовуються чинні freshness,
sequence та session правила діагностики.

Стара прошивка без цього блоку продовжує звичайне керування, але не
вмикає таймери. Оновлення сервера обов'язкове до прошивки: старий parser
не знає нових полів/причини `program_completed`.

План, API, UI та модель прогресу спільні для V3/V4/V5 і не залежать від
Wi-Fi. Реальний executor зараз з'єднаний із драйвером SU600 на V3;
симулятор перевіряє серверний шлях. LTE-адаптер V4, плата V5 та інші
VFD-профілі потребують власної реалізації й фізичного приймання.

## Оновлення налаштованого стенда Windows

Спочатку завершити RUN, перевірити STOP/0 Гц і виконати `DISARM` у Serial.
Зупинити сайт через Ctrl+C. Зберегти налаштований старий скетч поза Git,
`.env.demo`, `.env.v3`, сертифікати; для важливої історії виконати
[backup](backup-restore-v1.md). Наявні паролі й `config.local.h` не змінюються.

У PowerShell з кореня проєкту:

```powershell
Set-Location "C:\Users\seraf\Documents\TechBaza\techbaza-iot"
$sketchBackup = Join-Path (Split-Path (Get-Location) -Parent) ("kerumo_v3_before_040_" + (Get-Date -Format "yyyyMMdd_HHmmss"))
Copy-Item .\firmware\kerumo_v3 $sketchBackup -Recurse -ErrorAction Stop
git pull --ff-only origin main
if ($LASTEXITCODE -ne 0) { throw 'Не вдалося оновити код; збережіть повідомлення про конфлікт' }
docker compose -p techbaza-demo --env-file .env.demo -f compose.demo.yml stop backend simulator
if ($LASTEXITCODE -ne 0) { throw 'Не вдалося зупинити сервіси' }
docker compose -p techbaza-demo --env-file .env.demo -f compose.demo.yml build backend
if ($LASTEXITCODE -ne 0) { throw 'Помилка збірки backend' }
docker compose -p techbaza-demo --env-file .env.demo -f compose.demo.yml run --rm -T --no-deps backend alembic upgrade head
if ($LASTEXITCODE -ne 0) { throw 'Помилка міграції' }
docker compose -p techbaza-demo --env-file .env.demo -f compose.demo.yml run --rm -T --no-deps backend python -m app.demo.seed
if ($LASTEXITCODE -ne 0) { throw 'Не вдалося оновити demo capabilities' }
docker compose -p techbaza-demo --env-file .env.demo -f compose.demo.yml run --rm -T --no-deps backend python -m app.bench.su600 --enable-control-extended-test
if ($LASTEXITCODE -ne 0) { throw 'Не вдалося увімкнути можливості програм V3' }
docker compose -p techbaza-demo --env-file .env.demo -f compose.demo.yml up -d --no-build --no-deps --wait --wait-timeout 90 backend simulator
if ($LASTEXITCODE -ne 0) { throw 'Backend або simulator не запустився' }
Invoke-RestMethod http://127.0.0.1:8001/health
Set-Location frontend
npm.cmd ci
if ($LASTEXITCODE -ne 0) { throw 'Помилка встановлення frontend' }
npm.cmd run dev
```

Процедура передбачає вже запущені PostgreSQL, Mosquitto та V3 TLS gateway
попереднього стенда; gateway не потрібно перестворювати. `/health` має
показати **0.42.0**, Alembic head — `20261001_0020`. Повторний seed додає
відсутню capability симулятора; команда bench додає/вмикає `vfd.program` та `vfd.schedule`
для фізичного стенда, але не виконує ARM чи RUN. Змінений вручну профіль
не перезаписується автоматично. `prepare-v3.ps1` для цього оновлення не
запускати: він повертає read-only enrollment. `down -v` не потрібний.

Далі через Arduino IDE завантажити **весь скетч `firmware/kerumo_v3`**
по USB з попередніми налаштуваннями ESP32-S3 N16R8 і бібліотек.
У вже підготовленому моторному стенді зберегти локальні прапорці
`KERUMO_ENABLE_CONTROL` і `KERUMO_ENABLE_EXTENDED_TEST`; типові шаблони
залишають їх `false`. Не вмикати **Erase All Flash** і не стирати NVS.

0.4.0 мігрує попередній journal v0.1/v0.2/v0.3 зі збереженням UID, sequence,
історії та motion latch до нового формату. Некоректний журнал блокує
керування. Повернення старої прошивки після міграції може дати
`storage=LOCKED`; стирання NVS для обходу не є процедурою rollback.
Для rollback потрібне окреме узгодження стану сервера/контролера.

Serial Monitor **115200**: версія **0.4.0**, `storage=OK`, MQTT/TLS.
Після перевірки зупинки й чинної підготовки стенда ввести
**`ARM SU600 TEST`** у рядок Serial Monitor і надіслати з newline.
Короткий `ARM SU600` не дозволяє програми. Після ARM дочекатися свіжої
телеметрії; на сайті вибрати правильний фізичний пристрій.

## Приймання

Спочатку перевірити на **симуляторі**, потім повторити на підготовленому
V3 під наглядом оператора, використовуючи частоти вже погодженого
стенда. Фізичні F-параметри ця функція не переписує.

1. Звичайне керування: перевірити незмінні START/частоту/STOP.
2. Таймер: один етап на 30 с; відлік починається після досягнення частоти,
   наприкінці STOP/0 Гц, у журналі `succeeded` і `stop_confirmed=true`.
3. Програма: для наявного стенда 20 Гц/30 с → 30 Гц/30 с. Перевірити
   перехід, два завершені етапи та фінальний STOP. F5 між етапами не
   запускає програму вдруге, прогрес знову надходить із контролера.
4. На першому етапі натиснути STOP. Очікувати підтвердження зупинки,
   `program_cancelled`; другий етап не виконується навіть після F5.
5. У погодженому сценарії втрати gateway/RESET перевірити переривання,
   відсутність автоматичного продовження та необхідність місцевого ARM.
   Виміряти час зупинки; раніше прийнятий ручний RUN-тест не зараховувати
   автоматично як перевірку активної програми.
6. Зафіксувати revision, firmware, план, Serial, журнал/діагностику та
   підтвердження фактичного обертання/зупинки оператора.

Автоматичні регресії охоплюють строгий payload, права/profile/freshness,
HTTP/MQTT та симулятор, окремий deadline, duplicate/STOP, reboot,
мережеві й локальні відмови, 24-годинну межу/32-бітне переповнення,
міграцію реального binary layout старого журналу, F5 і мобільну форму.
Це не вимірювання навантаженого двигуна та не приймання V4/V5.
