## 2. Контекст і навігація

Організації, об’єкти та пристрої завантажуються з API. UUID у deep link не
вважається доказом доступу: перевіряються device → site → organization та
актуальний доступ користувача. Неактивна організація не стає робочим контекстом.
Breadcrumbs відповідають перевіреній ієрархії.

Списки показують по 20 записів із lookahead до 21 запису для визначення наступної
сторінки; frontend не вигадує загальну кількість. Початковий пошук default
organization обмежений першими 100 записами; повний каталог доступний посторінково.

У sessionStorage зберігаються лише перевірені IDs контексту з прив’язкою до
`user_id` та `auth_session_id`. Токени, назви й permissions туди не копіюються.
Після F5 контекст знову перевіряється. Видалений або чужий контекст не відновлюється.
Ключі кешу враховують session, tenant, site, device і page; при переході старі
запити скасовуються, а попередній вміст приховується до показу нового контексту.

## 3. Список пристроїв і бюджет запитів

Рядок містить назву, UID, тип і lifecycle. Availability розрізняє Online,
Offline, відсутність першого з’єднання та невідомий стан/помилку.

| Запит | Обмеження |
|---|---|
| Availability у списку | Максимум 4 одночасно для видимої сторінки до 20 пристроїв; timeout 5 секунд |
| Перехід між сторінками | Старі запити скасовуються; їх відповіді не підміняють нову сторінку |
| Overview пристрою | Один GET `/api/v1/devices/{id}/overview` на явне завантаження/оновлення після перевірки контексту |
| Overview timeout/retry | 10 секунд; автоматичний query retry вимкнений |
| Auth replay | Чинний auth adapter може один раз повторити GET після успішного refresh |
| Фонове оновлення | Polling відсутній; локальний timer не звертається до мережі |

На сторінці пристрою окремий availability GET не дублює дані overview.
`403/404` не залишає доступні раніше рядки чи показання на екрані.

## 4. Панель modules/channels

`/devices/{UUID}` показує реальний overview. Фіксований демонстраційний макет
перенесений до `/ui-kit/device-demo` і не видається за дані пристрою.

Склад карток визначається enabled assignments з backend. Numeric channels
отримують одиниці з API; boolean показуються як «Так»/«Ні». Нуль і `false`
зберігаються як валідні значення. Integer перевіряється в безпечному діапазоні
JavaScript. Відомі канали мають українські підписи, невідомі — безпечний fallback.

Command-only модуль пояснює призначення без кнопок керування. Непідтримуваний
тип показує явний fallback; порожній склад модулів має окремий стан.
Панель не додає випадкові канали зі старого raw telemetry snapshot.

Runtime-проєкція перевіряє device/site/org/UID, доступ, унікальність assignments,
capabilities і channels, одиниці, скінченність чисел, типи та узгодженість quality.
Raw snapshot/config не зберігаються у проєкції кешу. Власні ключі каналів
перевіряються через `Object.hasOwn`, включно з випадками `__proto__`/`constructor`.

## 5. Якість показань і зміни конфігурації

| Стан | Що бачить користувач |
|---|---|
| fresh | Валідне показання з актуальною позначкою якості |
| stale | Останнє відоме значення з попередженням, що це не поточний стан |
| missing | Тире та «Немає даних», без підстановки нуля |
| invalid | Тире та «Некоректні дані» |
| session_changed | Пояснення про попередню сесію контролера |
| future_timestamp / delayed_report | Пояснення проблеми часу або затримки |
| Online з простроченим timeout | Вимога оновити зв’язок; frontend не вигадує Offline |

Зв’язок і свіжість телеметрії — незалежні ознаки. Timer раз на секунду враховує
вік отримання на сервері, затримку reported time та час запиту. Повернення у
видиму вкладку також оновлює оцінку; timer очищується при unmount.

«Оновити панель» перечитує модулі, показання, permissions і presence атомарно.
Старі widgets приховуються під час запиту та після помилки. Вимкнений модуль
зникає, увімкнений повертається лише з нової відповіді. `gcTime: 0` прибирає
неактивний overview; logout і зміна контексту використовують чинне очищення кешу.

Viewer має read-only панель із перевіркою необхідних permissions. `401`
обробляється чинним session refresh/revoke, `403/404` — втратою доступу;
помилки сервера допускають явне повторне завантаження.

Конфігурація тут означає **відображення** змін, зроблених через backend API.
Редактор config, provisioning і write-форми enable/disable не реалізовані.
Віддалені зміни доступу чи модулів стають відомими при наступному запиті або
відновленні session; миттєвого push немає.

У PowerShell з кореня репозиторію, із запущеним Docker Desktop та зупиненим
попереднім Next.js server:

git pull --ff-only origin main
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-stage11-op3-op4.ps1 -Start

зберігає demo credentials/data та запускає frontend після PASS.

для таких пунктів у цій серії зображень немає:

2. Оновлення панелі, F5 та переходи між пристроями без залишкових показань.
3. Вузький екран і вихід у двох вкладках.

Відповідні автоматичні сценарії пройдені, але це не підміняє ручне приймання.

## 9. Обмеження і наступна точка

Реальні графіки історії, фонова політика оновлення, надсилання команд та журнал
lifecycle ще не реалізовані в цьому frontend. Alarms залишаються демонстраційними.

або навантаження 10 000 контролерів на основі цих тестів.
