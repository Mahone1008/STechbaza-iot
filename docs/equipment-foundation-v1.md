# Етап 1: обладнання, профілі й прив'язка команд

02.10.2026. Backend **0.44.0**, Alembic **0021**, firmware V3 **0.6.0**.
Це програмна основа [погодженого плану](next-stage-plan-vfd-service-qr.md).
Нове фізичне приймання 0.6.0 залишається відкритим.

## Що розділено

| Сутність | Призначення |
|---|---|
| Organization / User | Клієнт, обліковий запис і чинні права |
| Site | Місце з назвою та часовим поясом |
| PumpInstallation | Окрема насосна установка всередині об'єкта |
| Device | Фізичний контролер з власним UID, командами та історією |
| EquipmentModule | Конкретний модуль контролера: частотник, датчик тощо |
| EquipmentConfiguration | Незмінна ревізія конфігурації з автором, session ID і SHA-256 |

На контролері можуть бути кілька екземплярів одного типу; `slot` унікальний
лише в межах контролера. Реєстрація інвентарю не додає capabilities автоматично.
Поточна прошивка керує **одним** VFD на контролері. Незалежні канали кількох
датчиків та одночасне керування кількома VFD ще потребують реалізації.
До QR-етапу чинний `Device.site_id` залишається обов'язковим; окремий
виробничий реєстр неприв'язаних контролерів додається на етапі 2.

Паспорт модуля містить виробника, серію, точну модель, серійний номер,
апаратну й програмну ревізії. Відсутня ревізія лишається невідомою.
Паспорт двигуна зберігається окремо від профілю моделі та **не записується
автоматично у F/P-регістри**. Межі частоти й параметри шини входять у
конфігурацію конкретної установки, а не змінюють загальний профіль.

## Каталог і драйвери

Каталог зберігає версію, hash, назву/контрольну суму наданої інструкції,
номери сторінок PDF, сімейство параметрів та межу підтримки.

| Серії SUSWE | Стан у цьому етапі |
|---|---|
| SU600 | Драйвер v1 для стендового SU600A-5RG1-B; програмні регресії |
| SU100 | Документований запис каталогу, окремі P-регістри; керування заблоковано |
| SU300 | Документований запис; подібні адреси не вважаються доказом сумісності |
| SU700 / SU800 / SU900 / SU1000 | Окремі записи за спільною інструкцією; P/A-сімейство; керування заблоковано |

Повний сервісний довідник параметрів і розшифрувань аварій — робота етапу 4.
Не заявляється підтримка всіх модифікацій навіть однієї серії. Успішне
читання Modbus не визначає виробника/модель. Перед commissioning модель
підтверджує людина за шильдиком; автоматичної ідентифікації тут немає.

Спільне ядро `Controller` отримує `VfdDriver`, оперує Гц/А/В та нормалізованим
станом. Адреси, масштаби, F0/F4/F5/F6 і packed digits SU600 винесені в
`Su600Driver`. Native-тест запускає те саме ядро з тестовим драйвером без
Modbus, іншими станами й частотами 70–90 Гц. Це перевіряє розділення коду,
а не дозволяє такі частоти для реального SU600.

## Як підтверджується конфігурація

1. Адміністратор/призначений сервіс реєструє установку та модуль.
2. Backend створює бажану ревізію за `expected_revision`. Потрібні свіжі
   STOP/0 Гц/DISARM, вимкнені розклади й відсутність незавершених команд.
3. Зберігається канонічний manifest: UID, module ID, binding ID/generation,
   revision, профіль/hash, driver/version, шина та межі установки.
4. Прошивка парсить **ці самі байти**, перевіряє відому версію профілю й
   обчислює SHA-256 при старті. Невідомий профіль/UID/шина блокують VFD I/O.
5. Телеметрія повідомляє фактичний manifest/hash, драйвер і сумісність.
   Backend звіряє всі поля, поточний boot session та свіжість. UI розрізняє
   очікування, розбіжність, застарілі дані, несумісність і підтвердження.

`compatible` вимагає control build, справного сховища й перевіреного
стану конфігурації VFD. Це не дозвіл ARM і не доказ правильності шильдика,
монтажу або всіх моторних захистів. Наявні локальні interlocks діють окремо.
Стан, повідомлений контролером, зберігається в diagnostics кожного telemetry
sample та поточному snapshot; бажані ревізії зберігаються незмінними.

**MQTT command v3** містить `equipment_target` із binding ID, revision та
configuration hash. Backend перевіряє ціль при створенні й dispatch;
контролер відкидає невідповідний пакет до черги/Modbus.
HTTP-запит також несе target, який UI фіксує при відкритті підтвердження;
затриманий запит або ручний повтор не може отримати нову прив’язку автоматично. Зміна конфігурації
робить попередні команди недійсними. Заміна екземпляра VFD створює новий
module ID, binding ID та покоління навіть для тієї самої моделі.

NVS отримав wrapper зі hash конфігурації. Старі формати v0.1–v0.5
читаються, але журнал іншої конфігурації не відновлює рух/STOP на новому VFD.
Після зміни manifest контролер блокується до локального
`BIND EQUIPMENT STOPPED`: читання має підтвердити профіль, STOP і 0 Гц.
Попередній журнал архівується, sequence зберігається, новий починається
без команд/програми та без ARM. Пошкоджений журнал цією командою не стирається.

## Сумісне впровадження

Міграція не вгадує паспорти старих пристроїв. Без бажаної конфігурації та
без managed manifest зберігається legacy v2. **Захист цілі v3 не поширюється
на стару прошивку/неоформлене підключення.** Після створення бажаної
конфігурації сервер блокує керування до її підтвердження; автоматичного
повернення до legacy немає. Довільна фізична заміна без оформлення паспорта
не може надійно виявлятися цим обладнанням.

На етапі 1 manifest встановлюється локально під час commissioning.
QR-майстер, мережеве застосування конфігурації, режими місцевого/дистанційного
керування та редактор F/P сюди не входять. Штатні способи роботи, таймер,
етапи й розклади збережені. Оптовику не додається жодної ролі чи входу.

## API й локальний manifest

| Запит | Право / дія |
|---|---|
| `GET /api/v1/equipment/profiles` | Активний вхід; загальний каталог без tenant data |
| `POST /api/v1/sites/{id}/installations` | `capability.manage` у цьому об'єкті |
| `POST /api/v1/devices/{id}/equipment/modules` | `capability.manage`; установка з того самого об'єкта |
| `GET /api/v1/devices/{id}/equipment` | `device.read`; паспорт і стан підтвердження |
| `POST /api/v1/devices/{id}/equipment/configurations` | `capability.manage`, фізичні передумови, optimistic revision |
| `GET /api/v1/devices/{id}/equipment/manifest` | `capability.manage`; точні JSON-байти, ETag SHA-256 |

Чужий tenant повертає 404; роль без потрібного права — 403.
Viewer читає паспорт, але не створює конфігурацію. Реєстрація обмежена
100 установками на об'єкт і 32 модулями на контролер; поточне читання
обмежене цими списками. Аудит автора конфігурації не зникає після видалення сесії.

Приклад тіла конфігурації (UUID модуля — із власного паспорта):

```json
{
  "expected_revision": 0,
  "module_id": "11111111-1111-4111-8111-111111111111",
  "profile_id": "suswe.su600.modbus",
  "profile_version": 1,
  "bus": {"transport":"modbus_rtu", "address":1, "baud":9600, "parity":"none", "stop_bits":1},
  "frequency_limits": {"min_hz":20, "max_hz":45}
}
```

Збережений із API manifest передають helper-у в Python-середовищі backend:

```bash
python -m app.tools.equipment_manifest path/to/manifest.json --output path/to/equipment_config.local.h
```

Файл `equipment_config.local.h` розміщують поруч із `config.local.h` у
`firmware/kerumo_v3`. Helper не перезаписує наявний файл, не змінює secrets,
не прошиває контролер і не надсилає команд двигуну. Не додавати BOM/переноси
до завантажених JSON-байтів. Подальше складання/завантаження — за
[чинним runbook V3](v3-su600-bench.md), на зупиненому стенді. Не стирати NVS.
Після локальної прив'язки перевірити `verified` у паспорті, потім окремо
виконувати [процедуру локального дозволу](v3-su600-extended-test.md).

## Перевірки й навантаження

- Python: каталог і спільний із firmware fixture, строгий контракт, hash,
  boot/stale/driver mismatch, legacy/v3 fencing, межі частоти.
- PostgreSQL/HTTP: повторні модулі, tenant/RBAC, STOP/DISARM, optimistic
  revision, непідтримувані профілі, envelope v3, старі команди після заміни.
- Native C++ із ASan/UBSan: весь попередній набір, незалежний драйвер,
  межі установки, ціль команди, scoped journal та заборона recovery іншої прив'язки.
- ESP32 CI: read-only/control/extended і окремий managed build із SHA-256.
- Frontend: типи/контракти, unit, production build і Chromium; паспорт
  закритий за замовчуванням, не робить запитів до відкриття, не закривається
  при оновленні панелі й не виходить за межі екрана 320 px.

Hash обчислюється один раз при boot/commissioning; каталоги кешуються;
паспорт не опитується у фоні. Частоти Modbus-опитування й механіка
таймера/розкладу не збільшені. Нова прив'язка додає NVS-записи лише під час
commissioning; звичайний журнал команд зберігає свою попередню політику.
Замір CPU/струму/latency та фізичне приймання нового firmware — окремі докази,
яких автоматичні тести не підміняють.

Downgrade 0021 з наявними конфігураціями заборонений: не можна мовчки
видалити fencing. Старий backup залишається читабельним, але його відновлення
виконується чинною offline recovery-процедурою. Старе firmware також не
розпізнає новий NVS wrapper; зворотне оновлення потребує окремого плану.
