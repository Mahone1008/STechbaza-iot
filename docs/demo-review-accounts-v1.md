# Тестові входи для приймання ролей

Додаткові входи створюються окремо від чотирьох старих demo-користувачів.
Це email-ідентифікатори для входу в KERUMO, а не поштові скриньки.
Використовуються чинні auth routes, Argon2 та серверні правила доступу.

## Якщо втрачено застосунок автентифікації

Вихід із сайту та видалення запису в Authenticator не вимикають двоетапний
вхід. Налаштування зберігається в обліковому записі на сервері. Якщо залишився
резервний запис або резервна копія застосунку, відновіть його. Інакше відкрийте
«Відновити доступ» на сторінці входу, введіть логін, особистий ключ відновлення
та новий пароль. Попередні сесії завершаться, старий ключ перестане діяти,
а налаштування застосунку буде скинуто. Клієнт підключає його повторно за бажанням; platform admin обов’язково. Новий ключ показується один раз.

Для test superadmin ключ не створюється автоматично під час підготовки
demo-входів: його потрібно видати в «Безпека облікового запису» до втрати
доступу. Якщо ключа й резервної копії застосунку немає, самостійне відновлення
недоступне. Потрібне окреме втручання адміністратора локального demo-сервера
для конкретного облікового запису. Не видаляйте базу, том PostgreSQL або
файл паролів і не перевипускайте всі входи для виправлення одного акаунта.

Скидання налаштувань двоетапного входу не змінює права, обладнання чи історію.
Автоматичний загальнодоступний обхід другого фактора відсутній.

| Email | Platform role | Клієнт / роль | Що перевіряти |
|---|---|---|---|
| owner@kerumo-demo.example.com | user | A / owner | Власник: об'єкти, керування, учасники |
| admin@kerumo-demo.example.com | user | A / admin | Адміністратор клієнта з обмеженнями щодо owner |
| operator@kerumo-demo.example.com | user | A / operator | Команди без адміністрування учасників |
| viewer@kerumo-demo.example.com | user | A / viewer | Перегляд без команд |
| service@kerumo-demo.example.com | service_admin | A / service | Призначений клієнт, діагностика, capability config |
| superadmin@kerumo-demo.example.com | superadmin | Глобальний доступ | Усі клієнти demo-бази й адміністративні API |
| other@kerumo-demo.example.com | user | B / owner | Другий клієнт; доступ до A заборонено |
| new@kerumo-demo.example.com | user | Без організації | Порожній тестовий кабінет, додавання контролера |

`service_admin` не надає глобального доступу до всіх клієнтів. Membership
`service` виданий лише A і не дозволяє адмініструвати користувачів.
Цей demo fixture надає доступ до організації. Чинний membership API також
підтримує обмеження `site_ids` і строк `expires_at`; [контракт](membership-management-v1.md).
`superadmin` — окремий привілейований акаунт власника платформи.

`new@…` — наявний тестовий акаунт без комплекту й обладнання. Він не
імітує заводський вхід нового покупця. Після входу натисніть «Додати
контролер» і вкажіть QR/UUID та пароль активації придбаного комплекту.
Для перевірки нового покупця створіть особистий акаунт через `/register`,
підтвердьте пошту й додайте контролер за QR та закритим паролем активації.
Один акаунт використовується для всіх його контролерів.
Authenticator для клієнта необов'язковий; для factory superadmin потрібна
підтверджена MFA-сесія. [Контракт акаунтів і локальні листи](personal-accounts-v1.md).

Загальний редактор F/P та повний сервісний інтерфейс залишаються в
[погодженому плані](next-stage-plan-vfd-service-qr.md). Для `/factory`
тестовому superadmin треба налаштувати й підтвердити TOTP навіть на loopback.

## Створення на існуючому demo-стенді

Потрібні вже підготовлені `.env.demo`, міграції та `app.demo.seed`:
[інструкція demo-стенда](demo-stand-v1.md).
У PowerShell з кореня репозиторію:

```powershell
git pull --ff-only
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\create-demo-accounts.ps1 -ShowPasswords
```

Сценарій збирає актуальний backend image, чекає готовності окремої demo-БД
та створює входи однією транзакцією. Паролі генеруються криптографічним RNG,
по 40 символів, і зберігаються у `.local/demo-accounts/accounts.json`, який
вже виключений з Git. `-ShowPasswords` виводить email та пароль у локальний
термінал; без цього прапорця секрети не друкуються.

Якщо надано готовий JSON з паролями, можна застосувати саме його. Наприклад,
після завантаження `kerumo-demo-accounts.json` у стандартну папку Downloads:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\create-demo-accounts.ps1 -CredentialsFile "$env:USERPROFILE\Downloads\kerumo-demo-accounts.json" -ShowPasswords
```

Цей файл монтується лише для читання й залишається джерелом паролів для
повторних запусків. Значення не додаються до Git або образу контейнера.

Повтор тієї самої команди показує ті самі паролі. Вхід — через чинний
frontend, підключений до demo API `http://127.0.0.1:8001`; окремого сайту
для кожної ролі немає. Зміни frontend або прошивки для цих входів не потрібні.

Актуальний файл `.local/demo-accounts/accounts.json` містить тільки
поточний набір восьми паролів. Використовуйте його замість старих таблиць
із переписки. Видаляйте лише застарілі копії, а не цей файл. Якщо пароль
змінено через «Безпека», поточним є вже новий пароль із цього екрана;
старий файл автоматично не оновлюється.

Якщо пароль/роль/стан акаунта чи membership уже змінено, сценарій зупиниться
без скидання. Це також стосується нового покупця, якому вже видали доступ.
Видалення локального файла не змінює пароль у базі: нові випадкові значення
не збігатимуться, і повтор буде відхилено. Старі `@techbaza-demo.example.com`
входи та `.env.demo` залишаються чинними.

## Межі та перевірки

- Потрібні одночасно `TECHBAZA_DEMO_MODE=1`, БД `techbaza_demo` та очікувані
  активні організації demo A/B. До основної бази команда не застосовується.
- Email або UUID іншого користувача не перезаписується; пізній SQL-конфлікт
  скасовує весь набір. Повтор не повертає відкликані права й не активує акаунт.
- Unit tests перевіряють збереження паролів, rollback, справжній password login
  та RBAC. SQLite тут використовується лише для чотирьох таблиць акаунтів.
- Demo job CI двічі запускає PowerShell-сценарій на PostgreSQL, потім перевіряє
  вісім browser login через HTTP, доступ до організацій/учасників і відмову
  читання чужого пристрою за відомим UUID. Паролі не потрапляють у CI output.
- Перевірка входів не надсилає команд обладнанню. Фізичне приймання частотника
  та майбутніх сервісних записів залишається окремим завданням.

## Очистити готові приклади, зберігши паролі й права

Після оновлення backend до 0.49.0 і міграції 0026 виконайте з кореня:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\reset-demo-review.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\reset-demo-review.ps1 -Apply
```

Перший запуск лише показує обсяг. Другий зупиняє demo writers, зберігає
PostgreSQL backup у `.local/demo-reset/<час>/before-reset.dump` і очищує
однією транзакцією об'єкти, пристрої та їхні налаштування/історію у demo A/B
та організаціях, де всі власники є цими review-акаунтами. Чужа організація,
до якої review-користувача лише запросили, не очищується.
Заводські приклади цих пристроїв і ready комплекти, зареєстровані review-акаунтами,
видаляються. Реальні комплекти у чужих організаціях не вибираються.

Для восьми акаунтів скидаються Authenticator, recovery keys, повідомлення
про прочитання та активні сесії. Пошта, password hashes, platform roles,
membership roles/стан/обмеження залишаються точними. Організації зберігаються
порожніми, оскільки на них закріплені права. Не запускайте `app.demo.seed`
чи simulator після очистки: вони знову створять/очікуватимуть старі приклади.

Команда вимагає `TECHBAZA_DEMO_MODE=1`, саме БД `techbaza_demo`, точні
демонстраційні UUID/пошти, demo slugs і збіг усіх восьми чинних паролів
із `.local/demo-accounts/accounts.json`. Невідповідність зупиняє reset без змін.
Якщо пароль уже змінено через сайт, спочатку внесіть саме чинне значення
в локальний файл, не перевидавайте пароль у БД. Після reset увійдіть заново;
superadmin зможе налаштувати новий Authenticator для factory.
Збережіть backup приватно разом із незмінним account key із `.env.demo`.

Якщо приклад уже отримав MQTT credentials, reset спочатку чекає підтвердження
їх відкликання шлюзом. Недоступний шлюз зупиняє видалення БД. Сценарій
враховує наявні `.env.v3`/`.env.controllers` overlays, щоб зберегти налаштування
підключення backend. Перед reset фізичне обладнання має бути зупинене й DISARM.
