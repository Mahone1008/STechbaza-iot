# Тестові входи для приймання ролей

Додаткові входи створюються окремо від чотирьох старих demo-користувачів.
Це email-ідентифікатори для входу в KERUMO, а не поштові скриньки.
Використовуються чинні auth routes, Argon2 та серверні правила доступу.

| Email | Platform role | Клієнт / роль | Що перевіряти |
|---|---|---|---|
| owner@kerumo-demo.example.com | user | A / owner | Власник: об'єкти, керування, учасники |
| admin@kerumo-demo.example.com | user | A / admin | Адміністратор клієнта з обмеженнями щодо owner |
| operator@kerumo-demo.example.com | user | A / operator | Команди без адміністрування учасників |
| viewer@kerumo-demo.example.com | user | A / viewer | Перегляд без команд |
| service@kerumo-demo.example.com | service_admin | A / service | Призначений клієнт, діагностика, capability config |
| superadmin@kerumo-demo.example.com | superadmin | Глобальний доступ | Усі клієнти demo-бази й адміністративні API |
| other@kerumo-demo.example.com | user | B / owner | Другий клієнт; доступ до A заборонено |
| new@kerumo-demo.example.com | user | Без організації | Порожній кабінет нового покупця |

`service_admin` не надає глобального доступу до всіх клієнтів. Membership
`service` виданий лише A і не дозволяє адмініструвати користувачів.
Наразі межа такого призначення — організація; доступ до окремих об'єктів
та тимчасові дозволи належать до наступного етапу.
`superadmin` — окремий привілейований акаунт власника платформи.

Оптовику окремий вхід не потрібен: покупець сам активує придбаний контролер
і обирає модель частотника. Поставки обліковує наша команда всередині системи.

Ці входи не додають нові продуктові функції: QR-прив'язки,
загального редактора F/P та нового сервісного інтерфейсу
ще немає. Вони описані в [погодженому плані](next-stage-plan-vfd-service-qr.md).

## Створення на існуючому demo-стенді

Потрібні вже підготовлені `.env.demo`, міграції та `app.demo.seed`:
[інструкція demo-стенда](demo-stand-v1.md).
У PowerShell з кореня репозиторію:

```powershell
git pull --ff-only
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\create-demo-accounts.ps1 -ShowPasswords
```

Сценарій збирає актуальний backend image, чекає готовності окремої demo-БД
та створює входи однією транзакцією. Паролі генеруються криптографічним RNG,
по 40 символів, і зберігаються у `.local/demo-accounts/accounts.json`, який
вже виключений з Git. `-ShowPasswords` виводить email та пароль у локальний
термінал; без цього прапорця секрети не друкуються.

Якщо надано готовий JSON з паролями, можна застосувати саме його. Наприклад,
після завантаження `kerumo-demo-accounts.json` у стандартну папку Downloads:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\create-demo-accounts.ps1 -CredentialsFile "$env:USERPROFILE\Downloads\kerumo-demo-accounts.json" -ShowPasswords
```

Цей файл монтується лише для читання й залишається джерелом паролів для
повторних запусків. Значення не додаються до Git або образу контейнера.

Повтор тієї самої команди показує ті самі паролі. Вхід — через чинний
frontend, підключений до demo API `http://127.0.0.1:8001`; окремого сайту
для кожної ролі немає. Зміни frontend або прошивки для цих входів не потрібні.

Якщо пароль/роль/стан акаунта чи membership уже змінено, сценарій зупиниться
без скидання. Це також стосується нового покупця, якому вже видали доступ.
Видалення локального файла не змінює пароль у базі: нові випадкові значення
не збігатимуться, і повтор буде відхилено. Старі `@techbaza-demo.example.com`
входи та `.env.demo` залишаються чинними.

## Межі та перевірки

- Потрібні одночасно `TECHBAZA_DEMO_MODE=1`, БД `techbaza_demo` та очікувані
  активні організації demo A/B. До основної бази команда не застосовується.
- Email або UUID іншого користувача не перезаписується; пізній SQL-конфлікт
  скасовує весь набір. Повтор не повертає відкликані права й не активує акаунт.
- Unit tests перевіряють збереження паролів, rollback, справжній password login
  та RBAC. SQLite тут використовується лише для чотирьох таблиць акаунтів.
- Demo job CI двічі запускає PowerShell-сценарій на PostgreSQL, потім перевіряє
  вісім browser login через HTTP, доступ до організацій/учасників і відмову
  читання чужого пристрою за відомим UUID. Паролі не потрапляють у CI output.
- Перевірка входів не надсилає команд обладнанню. Фізичне приймання частотника
  та майбутніх сервісних записів залишається окремим завданням.
