# Етап 2: запуск, підключення, заміна та передача

Чинний software contract: backend **0.46.0**, Alembic **20261005_0023**,
firmware **0.7.0**. Програмний цикл реалізовано; фізичне приймання цієї
прошивки на вашому ESP32/SU600 виконується за чеклістом нижче. Попередні
стендові докази не переносяться автоматично на 0.7.0.

## 1. Оновити чинний сервер без втрати даних

PowerShell, корінь вашого клонованого репозиторію. Перед оновленням — STOP,
DISARM, вимкнені розклади. Збережіть локальні файли прошивки та
[backup БД](backup-restore-v1.md). Для установки до 05.10 потрібне
[перенесення account secret](account-key-operations-v1.md); наявні паролі
не генеруються повторно. Запущений frontend зупиніть через Ctrl+C.

```powershell
git pull --ff-only origin main
if ($LASTEXITCODE -ne 0) { throw 'Оновлення Git не виконано' }
$dc = @('compose', '-p', 'techbaza-demo', '--env-file', '.env.demo', '-f', 'compose.demo.yml')
docker @dc up -d --wait postgres mosquitto
if ($LASTEXITCODE -ne 0) { throw 'PostgreSQL/MQTT не запустилися' }
docker @dc stop backend simulator
docker @dc build backend
if ($LASTEXITCODE -ne 0) { throw 'Backend build failed' }
docker @dc run --rm -T --no-deps backend alembic upgrade head
if ($LASTEXITCODE -ne 0) { throw 'Migration failed' }
docker @dc up -d --no-build --wait --wait-timeout 90 backend simulator
if ($LASTEXITCODE -ne 0) { throw 'Backend failed to start' }
Invoke-RestMethod http://127.0.0.1:8001/health
docker @dc exec -T backend alembic current
```

Очікування: `0.46.0`, `20261005_0023 (head)`. Ця процедура не змінює
ключі legacy V3, частотник чи його локальний ARM. Для нової установки
спочатку [створіть demo](demo-stand-v1.md); seed потрібен тільки для
відсутніх demo-даних. `down -v` до робочого проєкту не застосовувати.

Окремий термінал для сайта на цьому ПК:

```powershell
Set-Location frontend
npm.cmd ci
if ($LASTEXITCODE -ne 0) { throw 'npm ci failed' }
$env:NEXT_PUBLIC_API_BASE_URL = 'http://127.0.0.1:8001'
npm.cmd run dev
```

Відкрити `http://127.0.0.1:3000`. [Тестові облікові записи](demo-review-accounts-v1.md)
готує `./scripts/create-demo-accounts.ps1`; персональні паролі залишаються
у `.local/demo-accounts`, не в документації. Для `/factory` потрібні
superadmin і підтверджений TOTP навіть на localhost.

## 2. Шлюз і HTTPS для нового QR-підключення

Потрібна стала приватна IPv4-адреса ПК, доступна телефону та ESP32.
Замініть приклад своєю адресою. Новий MQTT TLS використовує **8884**,
legacy V3 лишається на **8883**; переписувати його `.env.v3` не потрібно.
Підготовка повторювана: чинні ключі зберігаються, зміна IP не маскується
автоматичним перевипуском сертифіката.

```powershell
$ControllerIp = '192.168.31.100'
./scripts/prepare-controllers.ps1 -HostIp $ControllerIp
if ($LASTEXITCODE -ne 0) { throw 'Controller gateway setup failed' }
$dc2 = @('compose', '-p', 'techbaza-demo', '--env-file', '.env.demo', '--env-file', '.env.controllers', '-f', 'compose.demo.yml', '-f', 'compose.controllers.yml')
docker @dc2 up -d --build --wait --wait-timeout 90 backend simulator controller-gateway controller-https
if ($LASTEXITCODE -ne 0) { throw 'Controller services failed to start' }
```

Дозвольте в локальному firewall тільки потрібній домашній/стендовій мережі
порти 8443 і 8884. Admin MQTT 1884 не публікується на хості. Встановіть
**власний** `.local/controllers-ca.crt` як довірений CA на тестовий ПК і
телефон. На Windows у поточному користувачі:

```powershell
certutil.exe -user -addstore Root .local/controllers-ca.crt
```

Це довіра до вашого стендового CA. Не встановлюйте сторонній CA й не
вимикайте перевірку TLS. Після завершення стенда непотрібну довіру можна
видалити через `certmgr.msc`. На телефоні використайте системне встановлення
CA; конкретні кроки залежать від ОС. Для production потрібні власний домен,
публічний TLS та керований цикл сертифікатів — окремий deployment етапу 5.

Для перевірки QR **з телефона** frontend має слухати LAN, а API — HTTPS.
Зупиніть попередній frontend через Ctrl+C. В окремому PowerShell:

```powershell
Set-Location frontend
$ControllerIp = '192.168.31.100'
$env:NEXT_PUBLIC_API_BASE_URL = "https://${ControllerIp}:8443"
npm.cmd run build
if ($LASTEXITCODE -ne 0) { throw 'Frontend build failed' }
npm.cmd run start -- --hostname 0.0.0.0
```

На ПК і телефоні відкрити `https://192.168.31.100:8443`. HTTPS proxy
передає UI локальному frontend на 3000, API — backend. Docker Desktop
підтримує `host.docker.internal`; Compose також містить Linux host-gateway.
Публічний QR друкуйте з цією доступною адресою, а не з localhost.

Після підготовки контролерів наступні `up`/`restart` робочого backend
виконуйте з обома Compose-файлами та `.env.controllers`, інакше зникне
налаштування enrollment worker. Приклад звичайного запуску:

```powershell
docker @dc2 up -d --wait backend simulator controller-gateway controller-https
```

## 3. Заводський комплект і прошивка

1. Увійдіть як superadmin, у «Безпека» налаштуйте TOTP та підтвердіть сесію.
2. У `/factory` введіть реальні серійний номер, ревізію, партію та номер
   протоколу фізичної перевірки. Галочка фіксує відповідальність оператора;
   вона не виконує апаратний самотест.
3. Завантажте приватний JSON. Публічний QR містить тільки URL. Закрита
   картка покупця містить activation code, ім’я мережі й setup password.
   Bootstrap key залишається у виробника та прошивці.
4. Надрукуйте QR кнопкою у реєстрі. Сторінка друку приховує приватні поля.
5. За потреби запишіть постачання оптовику: це облік, без надання прав.

Генерація `factory_config.local.h` із завантаженого комплекту, з кореня
репозиторію (замініть шлях до JSON):

```powershell
$kit = (Resolve-Path '.local/factory-controller.json').Path
$out = (Resolve-Path 'firmware/kerumo_v3').Path
$ca = (Resolve-Path '.local/controllers-ca.crt').Path
$ControllerIp = '192.168.31.100'
docker @dc2 run --rm -T --no-deps -v "${kit}:/private/kit.json:ro" -v "${ca}:/private/ca.crt:ro" -v "${out}:/sketch" backend python -m app.tools.factory_config /private/kit.json --ca /private/ca.crt --api-url "https://${ControllerIp}:8443" --output /sketch/factory_config.local.h
if ($LASTEXITCODE -ne 0) { throw 'Factory file generation failed' }
```

Команда відмовляється перезаписувати наявний файл. Для перевипуску спершу
збережіть старий файл у приватній резервній копії. Не включайте старий
`equipment_config.local.h` у factory build. При переході legacy-контролера
збережіть його приватний `config.local.h` окремо й використайте чистий
`config.example.h`, щоб Wi-Fi попереднього користувача не лишився в binary.
Режими керування в чистому шаблоні вимкнені; вмикаються тільки після
[підготовки стенда](v3-su600-extended-test.md).

Прошийте **весь** `firmware/kerumo_v3` через Arduino IDE з чинними
налаштуваннями ESP32-S3 N16R8, ESP32 core 3.3.1, ArduinoJson 7.4.2 та
ArduinoMqttClient 0.1.8. `Erase All Flash`/стирання safety NVS не потрібні.
Serial 115200 має показати **0.7.0**. Новий factory key скидає тільки
мережевий кеш/підтвердження; журнал команд зберігається до безпечної
локальної переприв’язки. Самопуск після прошивки заборонений.

## 4. Перевірити шлях покупця

| Дія | Очікування |
|---|---|
| Відкрити QR без входу | Вхід/реєстрація з поверненням до цього контролера |
| Ввести неправильний activation code | Прив’язку відхилено, об’єкт не створено |
| Створити новий об’єкт із назвою/часовим поясом і правильним кодом | Одна прив’язка; повторне сканування не створює дублів |
| Для другого контролера вибрати свій наявний об’єкт | Окремий Device у тому самому Site |
| На новому контролері підключитися до `KERUMO-<перші 8 символів UUID>` | Потрібен setup password із закритої картки |
| Відкрити `http://192.168.4.1`, зберегти SSID/пароль домашньої мережі | ESP32 перезапускається; пароль не надсилається backend |
| У наявного контролера STOP/DISARM, BOOT на 3 секунди | Setup відкривається після локально прочитаного STOP; закривається через 10 хвилин або кнопкою |
| Повернути телефон до домашньої мережі, «Перевірити підключення» | Оновився `last_contact_at`; це ще не підтвердження RS485 |
| Вибрати модель/ревізію за шильдиком | Збережено паспорт; невідомий драйвер не отримує керування |
| «Обладнання → Налаштувати підключення» | Вибрати SU600 лише для перевіреної повної моделі, перевірити межі/паспорт двигуна, зберегти |
| Дочекатися доставки, відкрити setup і підтвердити обладнання | Контролер читає сумісний профіль і STOP/0 Гц; неспівпадіння не вмикає керування |
| Завершити setup, оновити паспорт | Збігаються revision/hash; стан `verified` за свіжою телеметрією |
| «Завершити налаштування», спочатку «Спостереження» | Телеметрія доступна; RUN не дозволено |
| Після підготовки моторного стенда явно вибрати випробування | Потрібні паспорт двигуна, сумісний firmware build та окремий локальний `ARM SU600 TEST` |

Якщо телефон намагається покинути Wi-Fi без Інтернету, підтвердіть локальне
підключення й відкрийте адресу вручну. Setup не має HTTP RUN/STOP endpoint.
Початкова конфігурація може бути створена до першої телеметрії: це лише
дозвіл на читання обраного профілю. Для керування потрібні локальне
підтвердження, збіг manifest, свіжий STOP і окремий ARM.

## 5. Перевірити заміну частотника

- До від’єднання обладнання: STOP, 0 Гц, DISARM, вимкнути всі розклади,
  дочекатися завершення команд. План електричного відключення виконує
  відповідальний за установку; показання 0 Гц не доводять відсутність напруги.
- У «Обладнання → Замінити частотник» внести нові виробника/серію/повну
  модель, серійний номер, апаратну/програмну ревізії та паспорт двигуна;
  зазначити причину й підтвердити безпечний стан.
- При stale/невідомому STOP, RUN, ARM, активному розкладі або команді —
  операцію відхилено. Наявний паспорт не змінюється.
- При успіху старий паспорт лишається як архів, керування блокується.
  Повтор старого запиту не створює другу заміну. Виконати фізичну заміну
  за процедурою ізоляції та заново налаштувати підключення.
- Нова конфігурація має нові `module_id`, `binding_id` і покоління прив’язки.
  Старі HTTP/MQTT команди не приймаються новою прив’язкою. Знову потрібні
  локальний STOP/readback, підтвердження паспорта та commissioning.
- SU100/SU300/SU700/800/900/1000 можна внести в паспорт. Керування ними
  лишається недоступним до реалізації та приймання відповідного драйвера.

Підключений legacy V3 теж має процедуру заміни; доставку manifest для нього
виконує [експорт у локальний header](equipment-foundation-v1.md).
Історія обмежена 32 модулями на Device; API не видаляє старі модулі автоматично.

## 6. Ключі, перепродаж і повернення

**Ротація.** «Обладнання → Керувати доступом → Оновити ключ»:
пароль, новий TOTP за наявності, причина й підтвердження. Брокер розриває
стару MQTT-сесію, старий пароль більше не працює. ESP32 отримує новий
ключ у наступному HTTPS polling; повторний RUN самостійно не відбувається.

**Відкликання.** Відкликати доступ можна і при втраті зв’язку. Це відключає
керування й планує durable revoke, але не є доказом фізичної зупинки.
503 означає, що намір збережено, а ACK брокера ще немає; worker повторює
його після відновлення. Для повернення доступу — ротація, свіжа телеметрія
та повторне завершення налаштування. Read capabilities не видаляються.

**Передача.** Тільки власник організації або superadmin. Потрібні свіжий
STOP/0 Гц/DISARM, вимкнені розклади та завершені команди. Після доказу
пароля/MFA старий Device архівується; до broker ACK контролер має стан
`releasing`, і новий покупець не може його прив’язати. Якщо відповідь 503,
повторіть завершення передачі після відновлення шлюзу.

Успішна передача показує **одноразовий** новий activation code, QR та
кнопку завантаження комплекту. Збережіть його до закриття сторінки.
Bootstrap key у комплект передачі не входить. Передайте покупцеві також
закриту картку setup Wi-Fi; він задає власну мережу локально.
Новий покупець створює новий Site/Device із UID наступного покоління,
вказує свій паспорт і фізично підтверджує обладнання. Старі користувачі,
команди, розклади й history до нової прив’язки не переходять. Старий
activation code відхиляється. Перевірте це входом обох клієнтів.

**Втрата одноразового комплекту / повернення на завод.** Виробник у
`/factory` ставить карантин: відкликаються MQTT і bootstrap/activation keys.
Після фізичного огляду й нового test reference — «Повернення та перевипуск
комплекту». Новий factory header потрібно прошити; старий bootstrap більше
не працює. За відсутності broker ACK нові ключі не видаються. Повернення
не видаляє tenant-історію. Заводське підтвердження не замінює hardware test.

## 7. Потрібні локальні перевірки

Backend перевіряється в **окремому Compose-проєкті** без портів робочого
backend і без звернень до фізичного контролера:

```powershell
./scripts/check-stage2.ps1
```

Скрипт створює свою PostgreSQL/MQTT, застосовує міграції, перевіряє
onboarding, equipment і lifecycle, видаляє тільки власний test-проєкт.
Не запускайте ручний `backend_check` у базі з активними runtime workers.

Frontend, з каталогу `frontend` (зупинити server на 3000, якщо потрібен
Playwright; його тестова збірка використовує локальну API-адресу):

```powershell
$env:NEXT_PUBLIC_API_BASE_URL = 'http://127.0.0.1:8001'
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run test:unit
npm.cmd run build
if ($LASTEXITCODE -ne 0) { throw 'Build failed' }
npm.cmd run browser:install
npm.cmd run test:browser -- tests/browser/controller-lifecycle.spec.ts tests/browser/onboarding.spec.ts tests/browser/equipment.spec.ts
```

Після цієї локальної збірки для телефона повторно зберіть frontend із
HTTPS API з розділу 2. Якщо CI тієї самої ревізії вже пройдено, повторювати
повний автоматичний набір на ПК не потрібно: достатньо запуску, потрібних
сценаріїв UI і фізичного чекліста.

Панель, Графіки, Розклади та Журнал перевірте одним коротким циклом:
актуальні показання/свіжість → зміна частоти в дозволених межах → ARM і
START/STOP на підготовленому стенді → короткий таймер/два етапи → один
календарний запуск → F5 → записи Result. На viewer немає дій зміни;
operator не може замінити паспорт/передати контролер. Service бачить лише
призначені Site до закінчення membership. При відключенні gateway й
перезапуску ESP32 підтвердити зупинку й відсутність самовідновлення.
Подробиці моторних тестів — [програми](control-programs-v1.md) і
[календар](control-schedules-v1.md); не дублюйте довгі soak-тести без нової причини.

## 8. Збереження та межі

Разом із БД зберігайте `.env.demo`, `.env.controllers`, заводські JSON/header
і **весь** `.local/controllers`, включно з `dynamic-security.json` та TLS.
Для узгодженого backup зупиніть backend і controller-gateway; не відновлюйте
стару БД поруч із новішим broker credential store як готову пару. Усі ці
файли приватні; CA certificate — публічна частина. Пропажа root secret
робить зашифровані MQTT/TOTP ключі недоступними.

Шлюз підготовки є локальним стендовим deployment. Масштабування, OTA,
flash encryption/secure boot, захист заводського виробництва, довгі
випробування та production certificate renewal залишаються окремими
роботами. LTE чекає конкретний модем. Драйвер керування реалізовано лише
для перевіреного SU600. Наявність програмного сценарію не є заявою про
виконане фізичне приймання всіх моделей.
