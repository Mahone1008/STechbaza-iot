# Етап 12.3 — Start / Stop / frequency

> Оновлення 0.39.0: поточні правила порядку команд, TTL, пізніх відповідей та міграції описані в [command-safety-v2.md](command-safety-v2.md).

Дата: 28.09.2026. Реалізовано разом із [12.4 — журналом](stage-12-op4-command-journal.md)
за дорученням користувача продовжити наступні дві операції.

## Поведінка

- Кнопки залежать одночасно від `command.execute`, призначених modules і
  серверних `allowed_commands`. Viewer має журнал без форми керування.
- Перед POST виконується новий GET overview: зміна capability/прав або offline
  блокує Start/frequency. Сервер перевіряє доступ повторно при POST.
- Частота: скінченне число 0–100 Гц, включно з нулем; порожнє поле не є нулем.
  Це межі протоколу, а не індивідуальні робочі межі частотника.
- TTL прийому: ціле 5–300 с, типово 30 с. Підтвердження показує пристрій,
  UID, дію, частоту та TTL. Для offline Stop показано очікування доставки
  й відсутність підтвердження фізичної зупинки.
- `request_id` генерується один раз після явного підтвердження. Синхронний
  захист не допускає подвійного POST при повторному кліку.
- POST не використовує автоматичні retries, зокрема після 401. HTTP 201/200
  означає реєстрацію/повернення існуючої команди; фізичний успіх не прогнозується.
- Відповідь перевіряється за device, organization, actor user, request_id,
  command_type, payload і TTL. Невідповідна відповідь не показується як успіх.

## Втрата відповіді та повтор

Network/timeout/5xx/некоректна відповідь після початку POST залишають стан
«Прийом команди не підтверджено». Сервер міг зберегти команду. Спочатку
пропонується перевірити журнал, а ручний повтор потребує підтвердження й
надсилає **той самий request_id і незмінне тіло**. Retry-After для 429
витримується; самовільного POST після таймера немає.

Монотонний локальний deadline обмежує повтор початковим TTL від рішення
користувача. Це додатковий клієнтський ліміт: серверний TTL починається від
створення durable record. Після deadline старий запит більше не надсилається.
Щоб перейти до нової дії після невизначеного результату, користувач явно
завершує перевірку; це **не скасовує попередню команду**.

Offline/hidden/unmount/logout скасовують очікування. Скасований transport
не гарантує скасування вже прийнятої сервером команди. Pending intent не
зберігається у browser storage; F5, reconnect і повернення на пристрій не
надсилають стару команду. Відповідь старого екрана не відновлює його стан.

## Перевірки

Unit: межі й нуль частоти, TTL, узгоджені allowed_commands, підміна receipt.
Chromium: підтвердження/скасування, подвійний клік, ручний idempotent retry,
F5, offline, TTL, 401/403/409/422/429, зміна capability, чужий receipt,
пізня відповідь після navigation, viewer/mobile.
Live: явний opt-in `KERUMO_RUN_COMMAND_DEMO=1`, лише localhost demo API,
UID `TB-DEMO-PUMP`, Stop через UI та реальний ACK/result simulator.
Перевірок фізичного обладнання ці тести не виконують.

Результати CI, Windows-команда та ручні сценарії — у [12.4](stage-12-op4-command-journal.md).
