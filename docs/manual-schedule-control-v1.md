# Ручне керування та робота за розкладом

Реалізовано 07.10.2026: backend **0.51.0**, міграція **0028**.
Уточнений запит користувача: усі команди надходять із сайта; фізичного
перемикача на стенді немає. Це режим автоматизації сервера, а не зміна
F0.02/F0.03 або джерела команд частотника. Firmware V3 залишається **0.8.1**.
Фізична частина LOCAL/REMOTE із [плану етапу 3](next-stage-plan-vfd-service-qr.md)
залишається відкритою.

## Поведінка для користувача

На панелі й у розділі «Розклади» видно збережений «Режим запуску».

| Режим | Поведінка |
|---|---|
| Ручне керування | Майбутні автоматичні запуски призупинено. Розклади та історія зберігаються. |
| За розкладом | Сервер виконує майбутні запуски увімкнених розкладів у часовому поясі об’єкта. Пропущені запуски не відновлюються. |

Вибір потребує підтвердження та записується в PostgreSQL, спільно для всіх
телефонів і вкладок. F5, вихід з акаунта та перезапуск сервера його не скидають.
Кнопки «Запустити» й «Зупинити» залишаються на панелі в обох режимах.
Чинні блокування запуску при offline, непідтвердженій конфігурації або
активній програмі зберігаються; STOP не залежить від актуальності ревізії режиму.

Ручний Start, STOP або запуск таймера/етапів атомарно переводить пристрій
у ручний режим. Наступний автоматичний запуск не втручається в ручну роботу.
Зміна частоти сама по собі не перемикає режим; під час активної програми її
контролює програма. Повтор уже прийнятого HTTP-запиту не перемикає режим
знову, навіть якщо інший користувач тим часом увімкнув розклади.

Вибір режиму не надсилає RUN або STOP. Уже прийнятий контролером цикл
продовжує свій план; його зупиняють кнопкою STOP. Опубліковану команду
не називаємо невиконаною: якщо її подальшу доставку скасовано, результат
позначається невизначеним. Зупинка підтверджується окремою відповіддю
контролера й актуальними показаннями.

Щоб перейти до розкладів, потрібні увімкнені `vfd.control`, `vfd.program`,
`vfd.schedule`, майбутній запуск хоча б одного увімкненого правила та
свіжа готовність сумісного контролера. Створення або редагування правила
не вмикає автоматизацію. Таймер, етапи, перегляд розкладів та TTL залишаються
в «Додаткові налаштування команди»; їхній вибір у формі не змінює серверний режим.

## Контракт і транзакції

- `GET /api/v1/devices/{device_id}/control-mode`: `device.read`, ізоляція організацій.
- `PATCH` того самого ресурсу: `command.execute`; `request_id`, `mode`
  (`manual`/`schedule`) та строгий `expected_revision`.
- Overview додає `control_mode`: режим, ревізію, час зміни, кількість
  увімкнених правил і найближчий майбутній старт. Відсутність поля старого
  API не перетворюється на вигаданий режим.
- HTTP-команда може передати `expected_control_mode_revision`; новий frontend
  фіксує її під час відкриття підтвердження й перевіряє перед POST. Старі
  клієнти без поля сумісні. STOP приймається також зі старою ревізією.
- Device-lock серіалізує вибір режиму, створення команди, календарний worker
  та доставку. Нові команди зберігають поточну і запитану ревізії окремо.
  Перед кожною доставкою/повтором non-STOP ревізія перевіряється знову.
- Зміна режиму припиняє доставку queued/published календарних запусків.
  Acknowledged цикл зберігає результат. Повторне ввімкнення не оживляє стару
  чергу; календарний старт, що почався до зміни режиму, пропускається.
- У ручному режимі worker записує `control_mode_manual` в історію пропущеного
  запуску й обчислює наступний момент. Поточне вікно не наздоганяється.
- Append-only device event `device.control_mode_changed` зберігає автора,
  організацію, сесію, попередній/новий режим, ревізію та причину. UUID
  явного PATCH використовується для постійної ідемпотентності. Інший автор,
  payload або організація не можуть повторно використати цей UUID.

Якщо відповідь загубилася, frontend блокує новий запуск і пропонує
«Перевірити збереження режиму» з тим самим UUID та незмінним запитом.
STOP залишається доступним. Жодна зміна режиму не записується в localStorage
і не ставиться в браузерну чергу для автоматичного повтору.

## Оновлення й сумісність

Оновити backend і виконати `alembic upgrade head` перед новим frontend.
Очікуються `/health.version = 0.51.0` та `20261007_0028 (head)`.
[Оновлення чинного стенда](staff-console-v1.md),
[backup/restore](backup-restore-v1.md). Робочі env, ключі й дані не скидати.

Міграція зберігає поведінку пристроїв із чинними увімкненими розкладами:
їхній початковий режим буде `schedule`, ревізія 0. Інші та нові пристрої
починають у `manual`. Це не новий дозвіл керування: чинні права автора,
capabilities, профіль, підтримка firmware, online та TTL перевіряються далі.
Протокол MQTT v2/v3, записи NVS і регістри SU600 не змінюються.
Для цієї зміни повторне завантаження прошивки не потрібне.

## Перевірки та ручне приймання

Автоматичні перевірки охоплюють PostgreSQL/HTTP/RBAC, оптимістичну ревізію,
гонку двох операторів, незмінний повтор запиту, відсутність моторної команди
при PATCH, пропуск ручного вікна, скасування старої черги після повторного
ввімкнення, пріоритет STOP та збереження старих функцій розкладів.
Browser-перевірки: 320/393/768/1280 px, F5, ручні кнопки в режимі розкладу,
втрата відповіді, незмінний повтор і read-only роль; WCAG/відсутність overflow.

На фізичному стенді окремо перевірити: збережений майбутній розклад не
запускається в ручному режимі; явне ввімкнення виконує наступне вікно;
ручний STOP припиняє цикл і призупиняє майбутні старти; повторне ввімкнення
не повертає перерваний цикл. Автоматичні тести не означають фізичного приймання.
