# V3 — перший фізичний стенд SU600 і сайт KERUMO

Стан на **30.09.2026**: базове читання на фізичному стенді ESP32-S3 N16R8 / SU600
з firmware **0.1.0** підтверджене користувачем. [Результати й відкриті перевірки](dossier-v3-su600-read-only-bench.md).
Подальше керування з firmware **0.2.1**, повторний пуск і три сценарії зупинки
прийняті в описаних циклах: [досьє керування V3](dossier-v3-su600-control-bench.md).
Повне приймання відмов і тривалої стабільності залишається відкритим.
Початковий режим — **тільки читання, без двигуна**. Це не production firmware та не завершення V4/V5.

Для firmware 0.2.1 є окрема [інструкція тривалих випробувань з двигуном](v3-su600-extended-test.md).
Вона прибирає 60-секундний ліміт лише в явно обраному сеансі й описує підготовку двигуна.

## Що перевіряємо

Сайт і backend на ПК → приватний demo MQTT broker → окремий TLS gateway :8883 →
ESP32 по локальному Wi-Fi → ізольований RS485 → SU600. Показання повертаються тим самим шляхом.

Фізичний UID: `KERUMO-V3-SU600-001`. Він не використовується симулятором.
Пристрій додається до існуючої організації **DEMO: клієнт A**, на окремий об'єкт
**V3 — фізичний стенд SU600**. Облікові записи, інші пристрої та історія зберігаються.
Під час підготовки створюється приватна копія PostgreSQL і SQLite у `backups/v3-*`.
Це копія перед зміною, а не повний перевірений disaster-recovery bundle.

## 1. Підготовка на Windows

Передумови: існуючий робочий demo з `.env.demo`, Docker Desktop у режимі Linux containers,
Git, Node/npm та Arduino IDE. Зупинити запущений Next.js через Ctrl+C.
ПК і ESP32 мають бути в одній LAN; ESP32 потрібен Wi-Fi 2.4 GHz і доступ до NTP.
Частотник у STOP; двигун не під'єднаний. Силову проводку змінюють лише при вимкненому живленні.

У терміналі VS Code з кореня репозиторію:

```powershell
git pull --ff-only
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\prepare-v3.ps1
```

Сценарій покаже IPv4 адреси та запитає адресу **ПК**, SSID і пароль Wi-Fi.
Обирати адресу фізичного Wi-Fi/Ethernet адаптера, не Docker/WSL/VPN і не адресу ESP32.
Наприклад, якщо ESP32 має `192.168.31.204`, адреса ПК може бути іншою в `192.168.31.*`.
Пароль вводиться приховано й не друкується. Існуючі сертифікати/секрети не ротуються.
Підготовка вимикає capability керування фізичним V3 також при повторному запуску.
Сценарій не виконує factory reset, `down -v`, не перепрошиває ESP32 і не запускає частотник.
Якщо він завершується помилкою — зберегти текст помилки; не видаляти volumes/credentials.

TLS gateway слухає тільки вибрану LAN адресу ПК. Для Windows Firewall потрібне правило
TCP 8883 лише для локальної підмережі й профілю **Private**. Якщо правила ще немає,
у PowerShell від адміністратора (домашня/довірена мережа має бути Private):

```powershell
if (-not (Get-NetFirewallRule -DisplayName 'KERUMO V3 MQTT LAN' -ErrorAction SilentlyContinue)) {
  New-NetFirewallRule -DisplayName 'KERUMO V3 MQTT LAN' -Direction Inbound -Action Allow `
    -Protocol TCP -LocalPort 8883 -RemoteAddress LocalSubnet -Profile Private
}
```

Не відкривати port forwarding на роутері. HTTP API і сайт залишаються локальними для ПК.
Якщо ПК змінив IP, сертифікат із прив'язкою до старої адреси потребує явного оновлення;
помилку перевірки TLS не можна обходити через `setInsecure()`.

## 2. Завантаження ESP32

Старий робочий скетч зберегти окремо. Відкрити **цілу папку скетчу**:
`firmware/kerumo_v3/kerumo_v3.ino`. Потрібні також файли `src/` та згенерований `config.local.h`.
Не переносити один `.ino` в порожню папку.

У менеджері плат: **esp32 by Espressif Systems 3.3.1**.
У менеджері бібліотек: **ArduinoJson 7.4.2** і **ArduinoMqttClient 0.1.8**.

| Налаштування Arduino IDE | Значення |
|---|---|
| Board | ESP32S3 Dev Module |
| Flash Size | 16MB (128Mb) |
| PSRAM | OPI PSRAM |
| Partition Scheme | 16M Flash (3MB APP/9.9MB FATFS) |
| USB CDC On Boot | Disabled для USB-UART; Enabled для native USB |
| Port | COM-порт підключеної ESP32 |
| Erase All Flash Before Sketch Upload | Disabled |
| Serial Monitor | 115200, Newline |

Використати той самий USB-порт і режим Serial, що працював у попередньому V3.
У досьє це був `USB Serial Port (COM10)`; номер COM після підключення може змінитися.
Для підключення через USB-UART обрати **Disabled**: Serial працює через UART0,
а RS485 — окремо через UART1. **Enabled** потрібне лише для native USB CDC.

UART лишається з попереднього V3: **RX GPIO18, TX GPIO17, 9600, 8N1, slave 1**.
Використовується перевірений ізольований конвертер з автоматичним керуванням напрямком.
Перевірити, що `config.local.h` містить `KERUMO_ENABLE_CONTROL false`, і натиснути Upload.
Після завантаження, якщо потрібно, натиснути RESET і відкрити Serial Monitor.

Очікуються `READ ONLY`, `storage=OK`, `MQTT CONNECTED / TLS`, діагностика `SU600:` і `READ:`.
Під час цього запуску **немає Modbus write навіть при завантаженні чи отриманні Stop**.
Налаштування частотника автоматично не переписуються.

## 3. Сайт

В іншому терміналі з кореня репозиторію:

```powershell
Set-Location .\frontend
if (-not (Test-Path .env.local)) { Copy-Item .env.example .env.local }
npm.cmd ci
if ($LASTEXITCODE -eq 0) { npm.cmd run dev }
```

Відкрити `http://127.0.0.1:3000`, увійти існуючим owner-акаунтом, вибрати клієнта A,
об'єкт **V3 — фізичний стенд SU600** та **V3 — реальний SU600 / ESP32-S3**.
Використовувати «Оновити панель»; автооновлення сайту за замовчуванням раз на 5 с,
телеметрія ESP32 — приблизно раз на 3 с. Пароль сайту лишився в `.env.demo`.

Для цього локального стенду адреса API у `frontend/.env.local` має бути
`NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8001`. Використовувати `127.0.0.1`
для сайту й API: поєднання сайту на `localhost` з API на `127.0.0.1`
заважає роботі refresh cookie з `SameSite=Strict`. Вхід може спочатку працювати,
але після F5 або оновлення access token браузер знову покаже форму входу.
Після входу на правильній адресі перевірити F5: сесія має відновитися без пароля,
а запит `POST /api/v1/auth/browser/refresh` — завершитися зі статусом 200.

Порівняти задану/вихідну частоту з панеллю SU600; для STOP без двигуна очікуються
вихідні 0 Hz / 0 A / 0 V, але тільки коли ці регістри реально прочитані.
Код помилки 0 означає прочитане «немає помилки». Відсутність даних не підміняється нулем.
RUN показує стан частотника, а не підтвердження обертання вала або подачі води.
Тиск, рівень води, ручний перемикач і аварійний вхід цьому стенду не призначені.

Надіслати скриншот панелі V3 і 2–3 блоки `SU600:` / `READ:` із Serial Monitor.
Не надсилати `config.local.h`, `.local/v3`, `.env.demo`, `.env.v3` або скриншоти паролів.

## 4. Перевірки читання та відмов

| Перевірка | Очікування |
|---|---|
| Перезапуск ESP32 | Новий session_id; без START/STOP записів у режимі читання; sequence команд не скидається |
| Відключення живлення ESP32 | Сайт переходить Offline приблизно через 15 с; натиснути оновлення панелі |
| Втрата Wi-Fi / gateway | Reconnect, без самовільного запуску; стара вибірка не видається за нову |
| Відсутність RS485, підготована при знеструмленому стенді | Контролер може бути Online, але `vfd_link=false`, частота/струм/стан недоступні |
| Інший F6.05 або невідома конфігурація | Відмова дозволу керування, діагностика у Serial |
| Немає NTP | Немає дозволу команд; TLS-підключення очікує коректний час |

## 5. Початковий обмежений тест керування без двигуна

Для вже перевіреного V3 з двигуном чинний сценарій —
[EXTENDED](v3-su600-extended-test.md). Нижче збережено окремий короткий
режим без двигуна з 60-секундним таймером; це не налаштування EXTENDED.

Цей пункт **не виконувати разом із першим запуском**. Спочатку перевірити журнал
і збіг показань. Стенд залишається без двигуна; навіть тоді U/V/W під RUN є небезпечними.
Профіль обирається вручну за шильдиком SU600. Читання параметрів не є автоматичним
визначенням виробника/моделі. Не приєднувати цю firmware до SU800/900 або іншого VFD.

Профіль перевіряє `F0.02=2`, `F0.03=6`, `F0.04=50.0`, `F0.05=50.0`, `F0.06=0`,
`F6.00=1`, `F6.01=0000`, `F6.04=1.00`, `F6.05=0`. `F6.02` та `F6.03` читаються для діагностики.
Інші значення потрібно розібрати окремо, не скидати налаштування навмання.

Для окремого погодженого тесту змінити **тільки** `KERUMO_ENABLE_CONTROL` на `true`
в локальному `config.local.h`, повторно скомпілювати й завантажити без стирання NVS.
Увімкнути capability саме фізичного стенда:

```powershell
docker compose -p techbaza-demo --env-file .env.demo -f compose.demo.yml exec -T backend `
  python -m app.bench.su600 --enable-control-bench-without-motor
```

Після `MQTT CONNECTED` у Serial надіслати **ARM SU600**. Дозвіл дається тільки при
перевіреній конфігурації, доступному сховищі, коректному часі, STOP і вихідних 0 Hz.
З сайту: встановити 10 Hz → звірити задану частоту → START → перевірити RUN → STOP.
Повторний ARM потрібний після Stop/втрати зв'язку/перезапуску. `DISARM` у Serial запускає
локальну зупинку, якщо був RUN. Після START локально запитується STOP через 60 с;
невдалі спроби повторюються до прочитаного STOP і 0 Hz. Це не апаратний аварійний захист.

Контролер не використовує віддалений reset fault, reverse, jog або записи параметрів F0/F6.
До двигуна й реального насоса потрібні окремі налаштування меж частоти, поведінки при
зникненні живлення ESP32, F6.02 та фізичних захистів. При вимкненій ESP32 її код не може
надіслати STOP; сам короткий тест без двигуна не доводить таку зупинку.
Пізніше її підтверджено в одному фізичному EXTENDED циклі через E485:
[досьє керування](dossier-v3-su600-control-bench.md).

## Протокол і межі реалізації

- MQTT command v2; ACK/Result v1, окремі UUID boot/message/command; TTL перевіряється за UTC.
- NVS зберігає монотонний `control_sequence`, можливий RUN та останні **8** відповідей.
  Старші витіснені команди ніколи не виконуються повторно: їх блокує sequence.
- Намір зберігається до Modbus write. Збій між write і результатом залишає результат
  невідомим; START не повторюється. Після reboot можливий RUN потребує перевіреної зупинки.
- ACK не означає виконання. FC06 echo не означає RUN/STOP. Успіх підтверджують регістри;
  якщо фізичний результат не підтверджено, firmware зберігає Unknown і backend переходить
  у `result_unknown` після свого deadline. Автоматично видавати `succeeded` заборонено.
- UART/керування живуть в окремій FreeRTOS task; є окрема зарезервована черга Stop.
  Операції RS485 мають кінцевий timeout, але це не hard realtime / SIL-rated control.
- Gateway: TLS з перевіркою CA/IP, пароль на UID, ACL лише власних topics, retained вимкнено.
  Внутрішній demo broker лишається приватним Docker-сервісом; це не production provisioning/PKI.
- Підмножина `config.telemetry_keys` обмежує advertised overview та series.
  Ingestion перевіряє відомі keys і enabled capabilities; цей UI-фільтр не є MQTT ACL.
  Відсутнє поле зберігає стару поведінку; сторонні канали не додаються через config.
- NVS не стирати для обходу sequence/config помилок. Заміна контролера, IP, сертифіката,
  відновлення старої БД та перенесення до іншої організації потребують окремої процедури.

Команда збірки для native USB, яку використовує CI:

```sh
arduino-cli compile --fqbn esp32:esp32:esp32s3:CDCOnBoot=cdc,FlashSize=16M,PSRAM=opi,PartitionScheme=app3M_fat9M_16MB firmware/kerumo_v3
```

CI також збирає варіант для USB-UART з `CDCOnBoot=default` (Disabled).
