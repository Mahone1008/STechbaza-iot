# Календарні розклади v1

Backend **0.43.0**, firmware V3 **0.5.0**, Alembic **20261001_0020**.
Режими: «Звичайне керування», «За таймером», «За етапами», **«За розкладом»**.
Календарне фізичне приймання **SCHEDULE-01 відкрите**. Раніше підтверджені
випробування [етапів 0.3.0](control-programs-v1.md) не підтверджують цей режим.

## Інтерфейс і правила

Розклади відкриваються тільки через **«Додаткові налаштування команди» →
«Режим роботи» → «За розкладом»**. Окремої постійної вкладки/кнопки під
керуванням немає. Згортання налаштувань приховує весь календар, зберігає
чернетку й призупиняє polling списку та історії. Перехід в інший режим
закриває редактор без збереження; F5 також скидає незбережену чернетку.

Спочатку показано збережені розклади й кнопку «Новий розклад». Редактор
замінює список: назва, групи запуску й зупинки, частота. Повторення/сезон,
зміни частоти та винятки розгортаються окремо; місяці роботи показані лише
для повторюваних правил. «До списку розкладів» закриває чернетку без запису.
Код календаря завантажується лише при виборі режиму. Читач із `command.read`
може вибрати цей режим, але не має кнопок створення, зміни чи керування.
Перед збереженням потрібен серверний preview найближчих п'яти запусків і
підтвердження дозволу майбутніх автоматичних запусків. Зміна полів скидає
попередній preview. Після F5 збережені
правила беруться із сервера; незбережена чернетка не запускається.

- Один раз; щодня; обрані дні тижня; кожні N днів від початкової дати;
  щомісяця; щороку в день/місяць початкової дати.
- Початкова/кінцева дата сезону включно; перелік активних місяців дозволяє,
  наприклад, зимовий сезон із переходом грудень → січень.
- До 100 дат без запуску. Виняток належить даті початку, навіть якщо STOP
  через кілька днів. Правило можна призупинити і знову увімкнути.
- Від хвилини до 7 діб (168 годин) місцевого інтервалу, до семи змін частоти
  всередині нього; кожен інтервал у формі — від хвилини.
- Усі частоти перевіряються за чинним профілем установки. Розклад не
  визначає тиск/обсяг води без відповідних встановлених датчиків.
- До 50 збережених правил на пристрій; редагування замінює правило,
  історичні ревізії зберігаються. Журнал показує останні 30 запусків правила.

Приклад: 01.10.2026 19:00 → 02.10.2026 02:00, Europe/Kyiv, 50 Гц:
сім годин календарного інтервалу. За потреби: 19:00 40 Гц, 21:00 50 Гц,
01:00 наступного дня 40 Гц. Частоти прикладу не є універсальною рекомендацією.

STOP запитується на заданій межі; фактичне гальмування задає частотник.
Перехід частоти не пересуває наступну календарну межу. Якщо частотник не
встиг досягти цілі до наступної межі/за 60 с, виконання переривається.
Це відрізняється від «За етапами», де витримка починається після досягнення
цільової частоти. Активний план незмінний; редагування правила стосується
майбутніх запусків, не переписує вже прийнятий контролером план.

## Як увімкнути розклад

1. Відкрити «Додаткові налаштування команди» → «За розкладом» → «Новий розклад».
2. Указати назву, майбутні дату/час запуску, день/час зупинки та перевірену частоту.
3. Натиснути **«Перевірити розклад»**, звірити дати найближчих запусків.
4. Натиснути **«Зберегти та увімкнути»**, потім **«Підтвердити розклад»**.
5. У списку мають з'явитися «Увімкнено» та найближчий запуск. Окрема кнопка
   RUN не потрібна: контролер стартує в цей час. Результат — «Історія запусків».

Для першої перевірки на підготовленому стенді вибрати старт через 2–3 хвилини
і тривалість 2 хвилини. Після підтвердженого STOP/0 Гц надіслати в Serial
`ARM SU600 TEST` (115200, Newline) та дочекатися свіжої телеметрії до старту.
Backend, MQTT і контролер повинні працювати; сайт можна закрити.

Для **тижня безперервної роботи**: «Один раз», «День зупинки» → **«Через 7 днів»**,
час зупинки такий самий, як час запуску. Наприклад, 01.10 10:00 → 08.10 10:00.
Для **окремих запусків протягом тижня**: «Повторення та сезон» → «За днями тижня»,
обрати дні й дату завершення періоду; тривалість кожного запуску задається окремо.
Період дії правила не обмежений одним тижнем.

Ліміт фактичної роботи — 168 годин: тиждень через осіннє переведення годинника
може дати 169 годин і буде пропущений у preview. У такому випадку зменшити
інтервал на годину та перевірити показані UTC/місцеві межі. Ліміт ручного таймера
й етапів залишається 24 години.

## Календар, роки й часові пояси

Використано стандартні Python `datetime`, `calendar`, `zoneinfo` та IANA
tzdata (залежність також для Windows). Період правила обмежено
50 календарними роками, датами 2000–2199. Firmware приймає UTC 2020–2199;
нові майбутні запуски сьогодні вкладаються в обидва діапазони. Timestamp у
протоколі/прошивці — 64-бітні мілісекунди; складання ESP32 перевіряє 64-bit time_t.

| Ситуація | Поведінка |
|---|---|
| Щороку 29 лютого | Лише високосні роки; 2100 не є високосним |
| Щомісяця 31-го | Місяць без 31-го пропускається |
| «Останній день місяця» | Фактичні 28/29/30/31 днів |
| Пропущений місцевий час при зміні offset | Весь запуск пропускається, якщо неможлива будь-яка його межа |
| Повторна місцева година | Перший момент (`fold=0`), без другого запуску |
| DST змінює тривалість/порядок | Обчислення в UTC; неможливий порядок або >168 год фактичної роботи пропускаються |
| Корекція UTC після прийняття | Монотонні межі активного виконання не пересуваються |

Неіснуючі дати/час не створюють UTC-запис запуску; вони відсутні в preview.
Дати календаря передбачувані, майбутні законодавчі правила часових поясів — ні.
Під час оновлення deployment оновлювати tzdata й перезапускати backend.
Наступний запуск переобчислюється щонайменше раз на добу; список років
наперед не матеріалізується. Часовий пояс правила відповідає об'єкту під
час збереження; зміна поясу об'єкта потребує перегляду наявних правил.

## Виконання та відмови

У v1 сервер доставляє команду **в момент запуску**, не завантажує автономний
календар наперед. Потрібні активні сервер, MQTT і контролер. Прийняття/перший
RUN допускаються в межах 30 с від призначеного старту; запізнення не продовжує
час роботи. TTL окремої доставки — 30 с; він не починається при збереженні
правила за місяць до старту. Контролер сам перевіряє календарне вікно.

Команда `vfd.schedule.start`: payload v1 містить `starts_at`, `stops_at`
(UTC RFC3339), `version: 1` та до восьми `steps` із `frequency_hz` і
`duration_seconds`. Сума інтервалів точно дорівнює різниці UTC-меж.
Команда створюється тільки календарним worker, не через звичайний POST commands.
Протокольна основа спільна з [MQTT v2](command-safety-v2.md).

Потрібні `vfd.control`, `vfd.program`, `vfd.schedule`, свіжа телеметрія,
`program.ready=true`, `program.supports_schedule=true`, STOP і робочий profile.
Firmware 0.5.0 передає `program.max_schedule_seconds=604800`; відсутнє поле
означає попередній ліміт 86400 с. Для ввімкнення правила довше доби потрібна
телеметрія сумісного контролера. Ліміт повторно перевіряється при фактичній
доставці; після заміни на стару прошивку запуск блокується з
`schedule_duration_unsupported`. Сумісність не визначається лише capability.
Формат NVS 0.4.0 не змінюється; перед оновленням/поверненням версії потрібні STOP і DISARM.
Перший RUN, зміни частоти, остаточний STOP і Result виконує спільний
локальний executor таймера/етапів. Повтор envelope повертає попередню відповідь.

| Подія | Наслідок |
|---|---|
| STOP користувача | Перериває поточний план; майбутні правила лишаються увімкненими |
| STOP після настання часу, але до створення команди | Цей запуск пропускається; збережена дата STOP запобігає гонці |
| Призупинення правила | Забороняє наступні запуски/повторну доставку; вже прийнятий запуск зупиняється окремим STOP |
| Зміна ревізії до доставки | Стара команда більше не доставляється |
| Немає зв'язку або локального допуску | Запуск пропущено; причина в журналі, пізнього самозапуску немає |
| Відновлення backup | Усі розклади призупиняються до перевірки та явного повторного увімкнення |
| Перезапуск backend | Збережені правила відновлюються; прострочений запуск пропускається |
| Мережевий збій/RESET ESP32 під час виконання | Чинна V3-політика STOP і DISARM; автоматичного продовження немає |
| Непідтверджений STOP | `result_unknown`/повтор STOP; успіх не вигадується |

V4/V5 зможуть використати спільний контракт. Їх LTE-адаптер, автономний
старт без сервера, RTC після знеструмлення та offline-політика ще не реалізовані.

## Права, транзакції та витрати

Читання — `command.read`; preview/створення/редагування/пауза — `command.execute`
у межах пристрою та організації. Ревізія зберігає actor/session, правило й стан.
Доручення переживає logout автора, але його активність, чинні права,
прив'язка організації та capabilities перевіряються при кожному запуску й dispatch.

Один індексований відбір у чинному command worker, до 100 правил за цикл.
Немає окремого потоку/процесу на пристрій. Порядок locks: Device → Schedule →
Command. Команда, occurrence і наступна дата фіксуються однією транзакцією;
унікальність `(schedule_id, starts_at)` діє між ревізіями та workers.
PUT із `expected_revision` захищає від перезапису чужих змін і повторного
створення після втрати HTTP-відповіді. Пропущені періоди не відтворюються
масовою чергою; журнал фіксує найстаріший очікуваний запуск і переходить до майбутніх.

Перетини перевіряються на 366 днів із переглядом запусків за попередні
7 діб. Перевіряються також повторення одного правила: запуск на 7 діб
не можна повторювати щодня. Суміжні інтервали дозволено; новий старт
приймається лише після підтвердженого STOP попереднього виконання.
На довшому горизонті гарантується блокування зайнятого пристрою під час
фактичного запуску; запуски не підміняють ручне керування і не стають у чергу
«виконати потім». Закритий редактор не опитує розклади; відкритий список —
30 с, обрана історія — 15 с, із чинними backoff/visibility/session guards.
Це архітектурні обмеження витрат, не приймання одночасного старту 10 000 пристроїв.
Навантажувальні fleet/soak тести залишаються у [production-плані](project-status.md).

## Оновлення і перевірка

Виконати актуальну [процедуру оновлення Windows](control-programs-v1.md):
зупинка/Serial DISARM, копія попереднього скетча, pull, backend build,
`alembic upgrade head`, demo seed, `app.bench.su600 --enable-control-extended-test`,
перезапуск backend/simulator і frontend. Вона не змінює локальні secrets та
не запускає насос. Потім завантажити весь скетч **0.5.0** по USB без стирання NVS.
Міграція з 0.1/0.2/0.3 зберігає UID, sequence, журнал і незавершений intent;
повернення старої прошивки після цього не є готовою rollback-процедурою.

Спочатку перевірити на симуляторі, потім — на вже підготовленому стенді V3:

1. Створити разовий запуск на 2–3 хв у майбутньому, тривалість 2 хв,
   частота з уже перевіреного робочого діапазону. Перевірити preview,
   підтвердження, найближчий запуск і збереження після F5.
2. Дочекатися початку й STOP за календарними межами; звірити ACK/Result,
   `stop_confirmed` і фізичне обертання/зупинку.
3. Додати зміну частоти через хвилину. Перевірити перехід, потім повторити
   зі STOP до переходу — наступна частота не повинна виконатися.
4. Призупинити наступний розклад до старту; переконатися у відсутності RUN.
5. Окремо перевірити offline у момент старту, прострочення під час простою
   сервера, втрату gateway та RESET під RUN; після повернення немає самозапуску.
6. Зберегти версії/SHA, Serial, часові межі, журнал і підтвердження оператора.

## Розширення до 7 діб — 01.10.2026

Backend 0.43.0 / firmware 0.5.0 додають ліміт 604800 с, дні зупинки й
зміни частоти 0–7, перевірку підтримки контролером, перетини за попередній
тиждень і перевірку повторень одного правила. Таймер/етапи зберігають 24 год.
Форма пояснює послідовність перевірки, збереження та автоматичного старту.

Локально перевірено 112 backend-тестів; 109 інтеграційних тестів із
PostgreSQL/MQTT пропущено через відсутність цих сервісів у локальному середовищі.
Також пройшли 107 frontend unit, 21 browser-сценарій календаря/програм,
typecheck, lint, API generation/verification, build/budget та перевірка документації.
Нативний C++ suite з ASan/UBSan перевірив 7 діб, перехід 32-bit millis,
граничну тривалість, STOP, втрату мережі та reboot без відновлення. Лише
LeakSanitizer вимкнено локально через обмеження читання `/proc`; CI запускає
повну конфігурацію. Повний PostgreSQL/MQTT suite і складання ESP32 перевіряє CI.
Фізичне тривале приймання цієї версії залишається відкритим.
