# Стандарти розробки TechBaza

Цей документ фіксує базові правила якості коду та документації для всього проєкту TechBaza.

## 1. Загальний принцип

TechBaza розробляється як продукт, який має бути придатним не лише для прототипування, а й для подальшого production-використання.

Кожне нове рішення повинно бути:

- зрозумілим;
- модульним;
- тестованим;
- безпечним;
- документованим;
- придатним до масштабування;
- без зайвої жорсткої прив'язки до одного типу обладнання.

## 2. Мова документації та коментарів

Внутрішня документація проєкту ведеться українською мовою.

Українською пишуться:

- README;
- архітектурні нотатки;
- пояснення рішень;
- коментарі до нетривіальної логіки;
- docstring-и там, де вони потрібні;
- інструкції з запуску та обслуговування.

Назви класів, функцій, змінних, API-полів, topic-ів та технічних ідентифікаторів залишаються англійською відповідно до загальноприйнятої практики розробки.

## 3. Коментарі в коді

Коментарі не повинні дублювати очевидний код.

Погано:

```python
# Збільшуємо i на 1
i += 1
```

Добре:

```python
# Повторне підключення виконується з затримкою, щоб не створювати
# безперервний цикл запитів при втраті MQTT-брокера.
client.reconnect_delay_set(min_delay=1, max_delay=30)
```

Коментар повинен пояснювати причину, обмеження або архітектурне рішення.

## 4. Backend

Для backend використовуються:

- Python;
- FastAPI;
- SQLAlchemy;
- psycopg;
- Alembic;
- Pydantic;
- paho-mqtt.

Правила:

- API-маршрути не містять бізнес-логіку напряму;
- робота з БД відокремлюється від HTTP-рівня;
- MQTT-логіка відокремлюється від API;
- конфігурація зберігається через environment variables;
- секрети не комітяться в Git;
- помилки повертаються у передбачуваному форматі;
- логування має бути структурованим;
- критичні операції повинні мати audit trail.

## 5. Frontend

Для frontend використовуються TypeScript, React та Next.js.

Правила:

- TypeScript без неявного `any`;
- компоненти мають бути невеликими та повторно використовуваними;
- бізнес-логіка не змішується з presentation-рівнем;
- права доступу перевіряються не лише на frontend;
- UI відображає лише ті capabilities, які реально доступні конкретному об'єкту;
- loading, empty, error та offline-стани мають бути передбачені.

## 6. Firmware

Прошивка ESP32 повинна бути модульною.

Окремі модулі:

- Modbus;
- MQTT;
- connectivity;
- configuration;
- safety logic;
- telemetry;
- command handling;
- local fallback.

Критичне керування насосом не повинно повністю залежати від хмарного сервера.

При втраті Інтернету контролер повинен переходити в передбачуваний безпечний стан або продовжувати дозволену локальну логіку.

## 7. База даних

Зміни структури PostgreSQL виконуються через міграції.

Не допускається ручне редагування production-схеми без зафіксованої міграції.

Модель даних повинна підтримувати модульну архітектуру TechBaza:

```text
Site
  ↓
Device
  ↓
Installed capabilities
  ↓
Sensors / actuators / modules
```

Система не повинна припускати однаковий набір обладнання для всіх клієнтів.

## 8. API

API повинно мати:

- версіонування;
- чіткі request/response-моделі;
- валідацію;
- однакову структуру помилок;
- OpenAPI-документацію;
- перевірку авторизації на сервері;
- ідемпотентність там, де це необхідно.

Критичні команди керування повинні мати ідентифікатор команди та підтвердження виконання.

## 9. MQTT

MQTT topic-и повинні мати передбачувану структуру.

Майбутній принцип:

```text
techbaza/{device_id}/telemetry
techbaza/{device_id}/state
techbaza/{device_id}/events
techbaza/{device_id}/commands
techbaza/{device_id}/ack
```

Production-вимоги:

- TLS;
- окремі credentials для пристроїв;
- ACL;
- заборона anonymous access;
- обмеження доступу до topic-ів;
- контроль дублювання та повторної доставки команд.

## 10. Безпека

У Git не повинні потрапляти:

- паролі;
- API keys;
- приватні ключі;
- production certificates;
- реальні device secrets.

Критичні дії користувача повинні перевірятися backend-ом незалежно від frontend.

## 11. Git та зміни

Кожна логічна зміна повинна мати зрозумілий commit message.

Не змішувати в одному commit:

- рефакторинг;
- нову функціональність;
- виправлення помилки;
- випадкові форматування великої кількості файлів.

Перед значними змінами слід зберігати працездатний стан.

## 12. Тестування

У міру розвитку проєкту додаються:

- unit tests;
- integration tests;
- API tests;
- database migration tests;
- MQTT integration tests;
- simulator-based tests;
- hardware-in-the-loop tests для критичної логіки.

## 13. Definition of Done

Функція не вважається завершеною, якщо вона лише «працює один раз».

Перед закриттям операції перевіряються:

1. код запускається;
2. помилки обробляються;
3. конфігурація не зашита жорстко без потреби;
4. документація оновлена;
5. немає секретів у Git;
6. поведінка перевірена тестом;
7. архітектура не порушує модульний принцип TechBaza;
8. результат можна відтворити після нового `git clone`.

## 14. Основне правило

Код TechBaza має бути написаний так, щоб через декілька місяців інший розробник міг відкрити репозиторій, зрозуміти структуру системи та продовжити роботу без необхідності вгадувати, чому були прийняті ті чи інші рішення.
