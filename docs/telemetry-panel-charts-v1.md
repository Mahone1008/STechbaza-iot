# Показання панелі та графіки v1

Етап 8, операція 3. Backend **0.34.0**, migration **20260926_0017**.
Це backend-контракт майбутнього інтерфейсу. Сам UI належить Етапу 9.
Статус перевірок та приймання: [журнал Етапу 8](stage-8-test-backend.md).

## 1. Навіщо потрібна операція

Heartbeat доводить недавній зв'язок із контролером, але не свіжість
вимірювань. Панель повинна розрізняти справжній нуль, відсутнє значення,
некоректне значення і старе показання. Графік повинен показувати пропуски
та обмежувати навантаження на базу, не маскувати обрізану історію як повну.

Використовується наявний device overview; другого конкуруючого API панелі
та дубльованої політики capabilities не створено.

## 2. Якість поточних показань

`GET /api/v1/devices/{device_id}/overview` доповнено двома полями.
Успішна відповідь має `Cache-Control: no-store`.

### telemetry_freshness

| Поле | Значення |
|---|---|
| status | missing, fresh або stale |
| reason | no_telemetry, recent, session_changed, future_timestamp, timeout, delayed_report |
| received_at | Час приймання останнього snapshot сервером або null |
| reported_at | Час, повідомлений контролером, або null |
| received_age_seconds | Вік приймання; не менше 0; null до першого snapshot |
| stale_after_seconds | Налаштований поріг давності |

`TELEMETRY_STALE_AFTER_SECONDS=120` за замовчуванням, допустимо 1..86400.
Параметр передано через Compose і задокументовано в `.env.example`.
Неправильна конфігурація зупиняє запуск, а не вимикає перевірку мовчки.

Причина обирається в такому порядку:

1. Немає snapshot: missing / no_telemetry.
2. Відома поточна device session відрізняється від session snapshot:
   stale / session_changed. Новий heartbeat не робить старі показання свіжими.
3. Серверний received_at у майбутньому або reported_at більш ніж на
   30 секунд у майбутньому: stale / future_timestamp.
4. Received age перевищує поріг: stale / timeout.
5. Reported age перевищує поріг: stale / delayed_report.
6. Інакше fresh / recent; рівно на межі порогу значення ще fresh.

Reported time контролюється консервативно і може бути неточним через
годинник пристрою. Статус fresh означає проходження цих перевірок,
а не доказ справності датчика або незалежний час фізичного вимірювання.
Якщо reported_at відсутній, оцінка спирається на приймання і session.

### readings

Масив лише підтримуваних числових ключів enabled capabilities:

```json
{
  "key": "pressure.bar",
  "unit": "bar",
  "value": 0.0,
  "status": "fresh"
}
```

| status | Правило для value | Поведінка UI |
|---|---|---|
| missing | Ключ відсутній або null | «Немає даних», без нуля |
| invalid | Boolean, рядок, масив, об'єкт або число поза скінченним float | «Некоректні дані», value null |
| fresh | Скінченне число, пакет fresh | Показати число та одиницю |
| stale | Скінченне число, пакет stale | Показати число як застаріле і час даних |

Нуль є валідним числом. `false` зберігається у state, але не перетворюється
на 0 у числовій метриці. Snapshot є останнім прийнятим поточним пакетом;
ключі часткового пакета не переносяться з попереднього. Незалежних
timestamp для кожного сенсора поточний протокол не містить.

Overview очищує некоректні numeric values до null лише у DTO. Raw history
та збережений snapshot не змінюються. Значення вимкнених модулів приховано.

## 3. API графіка

`GET /api/v1/devices/{device_id}/telemetry/series`

| Query | Вимоги |
|---|---|
| metric | Один підтримуваний числовий ключ, 1..96 символів |
| start | ISO 8601 з часовим поясом, початок включно |
| end | ISO 8601 з часовим поясом, кінець не включно |
| bucket_seconds | Ціле 1..86400, за замовчуванням 300 |

Потрібно `start < end`; не більше 7 днів і
`ceil((end-start)/bucket_seconds) <= 1000`. Зайві query-параметри відхиляються.
Час нормалізується в UTC. У URL знак `+` часового поясу кодується як `%2B`;
для UTC зручно використовувати `Z`.

| metric | Capability | unit |
|---|---|---|
| vfd.frequency_hz | vfd.frequency.read | Hz |
| vfd.current_a | vfd.current.read | A |
| pressure.bar | pressure.read | bar |
| water_level.percent | water_level.read | % |

Відповідність capability береться з чинної telemetry_policy;
окремий словник містить лише одиниці. Довільне поле JSON не стає метрикою.
Для discrete state, наприклад pump_running, середнє не обчислюється.

Приклад запиту з власним UUID і JWT:

```http
GET /api/v1/devices/{device_id}/telemetry/series?metric=pressure.bar&start=2026-09-26T10:00:00Z&end=2026-09-26T11:00:00Z&bucket_seconds=300
Authorization: Bearer <access_token>
```

## 4. Семантика відповіді

Верхній рівень: device_id, metric, unit, start, end, bucket_seconds,
time_basis, generated_at, message_count, sample_count, max_messages, buckets.
`time_basis` завжди **server_received_at**. Це вісь приймання сервером,
а не гарантований час фізичного вимірювання. Історія включає збережені
пізні пакети, навіть якщо вони не оновили поточний snapshot.

Кожен bucket містить start, end, status, sample_count, missing_count,
invalid_count, minimum, maximum, average. Інтервали починаються від query.start,
а не від календарної «круглої» години. Останній інтервал може бути коротшим.
Пакет рівно на end не включається; на спільній межі належить наступному bucket.

- minimum/maximum — мінімум/максимум валідних чисел.
- average — середнє валідних зразків, не середнє за тривалістю.
- sample_count — кількість валідних чисел; missing_count — відсутніх/null;
  invalid_count — усіх інших значень у пакетах.
- message_count — усі пакети цього пристрою в періоді, включно з тими,
  де потрібної метрики немає; sample_count верхнього рівня — сума валідних.
- Порожній інтервал має null агрегати і всі counts = 0.
- Інтервал із пакетами без метрики також має null агрегати, але missing_count > 0.
- Інтерполяції, перенесення останнього значення та вигаданих нулів немає.

| status | Значення |
|---|---|
| ok | Усі значення числові та валідні |
| partial | Є валідні та відсутні/некоректні значення |
| missing | Пакети є, метрика скрізь відсутня/null |
| invalid | Валідних немає, принаймні одне значення некоректне |
| empty | У bucket немає пакетів |

SQL використовує Numeric для average, щоб сума великих скінченних
чисел не переповнювала float. Межа повернення — скінченний Python/JSON float.
Це перевірка типу й представлення, не калібрування датчика або фізично
допустимий діапазон тиску/струму конкретної установки.

## 5. Доступ, помилки та навантаження

Потрібна дійсна JWT session, доступ до активного tenant та device.read,
telemetry.read, capability.read. Viewer може читати. Superadmin має
чинний платформний bypass. Вимкнена чи непризначена capability не відкриває
графік, навіть якщо відповідні історичні значення залишилися в БД.

| HTTP | Причина |
|---|---|
| 401 | Немає дійсної session |
| 403 | Немає потрібного permission або користувача вимкнено |
| 404 | Пристрій відсутній або недоступний tenant; однакова відповідь |
| 409 | Capability вимкнена або не призначена |
| 422 | Невідома/нечислова метрика, помилка query, завеликий період або понад 100000 пакетів |
| 503 | Помилка сховища або перевищення SQL timeout |

Validation 422 має detail-масив, business 422 — detail-рядок. Інтерфейс
не повинен визначати тип помилки порівнянням точного тексту.
Успіх має `Cache-Control: no-store`.

База читає максимум 100001 пакет для виявлення перевищення бюджету.
Понад 100000 повертається 422, частковий графік не видається за повний.
Збільшення bucket_seconds зменшує кількість точок, але не кількість
вхідних пакетів; для перевищення packet limit потрібно скоротити період.
SQL statement_timeout = 3000 ms встановлюється LOCAL у транзакції запиту
і не переходить до наступного користувача connection pool.

Міграція 0017 замінює індекс telemetry_messages на
(device_id, received_at, id), не видаляючи дані. Downgrade відновлює
попередній двоколонковий індекс. Для цього тестового стенда backend
зупиняється на час міграції; створення індексу не є online migration.
Для великої production-бази потрібен окремий план безперервної міграції.

## 6. Автоматичні перевірки

Сім unit tests та тринадцять PostgreSQL integration tests перевіряють:

- UTC/offset, обов'язковий timezone, start/end, 7 днів і 1000 buckets;
- порожню історію, нуль, min/max/average, null/boolean/string/object;
- числа 1e308 та історичний JSONB 1e1000 без аварійного JSON/AVG overflow;
- рівно початок/кінець, короткий останній bucket, окремий чужий device;
- received_at як вісь незалежно від sent_at пристрою;
- tenant isolation, відкликання membership і permission, capability disable;
- відхилення невідомої метрики, зайвих query і некоректного періоду;
- явне перевищення packet budget та відсутність витоку statement_timeout;
- керований 503 при збої SQL;
- свіжий heartbeat зі старими показаннями та зміну device session;
- invalid/null у DTO без зміни БД, збереження state false;
- стабільне сортування сирої історії при однаковому timestamp;
- OpenAPI поля, query, Bearer security та коди відповідей.

Повний набір становить 74 unittest tests плюс окрема Chromium-перевірка
авторизації у CI. Результати не вважаються підтвердженими лише через
наявність тестового коду: точні запуски наведені в журналі Етапу 8.

## 7. Межі операції

Немає нового frontend, організаційного dashboard, постійної demo-сцени,
retention/архівації, materialized rollups або необмеженого експорту.
Доступ до історії, як у чинному raw telemetry API, визначає поточна
приналежність пристрою. Окремої tenant-власності кожного telemetry packet
і сценарію перенесення пристрою між клієнтами ця операція не вводить.
Фізичні діапазони сенсорів і їхня метрологічна якість потребують окремого
обладнання/конфігурації. Наступна операція — демонстраційний стенд після
приймання цього блоку користувачем.
