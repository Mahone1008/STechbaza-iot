# Безпечний порядок команд — backend 0.39.0

Міграція: `20260929_0018`. Outbound MQTT command: `schema_version: 2`.
ACK та Result зберігають envelope v1. Історичні документи v1 описують попередній контракт; наведені нижче правила мають пріоритет.

## Що означає час на прийняття команди

TTL — час від реєстрації команди сервером до `expires_at`, протягом якого контролер може **вперше прийняти її до виконання**. Типово 30 с, дозволено 5–300 с. Це не тривалість роботи насоса: після Start він не вимкнеться через TTL. Для зупинки потрібні Stop та локальні захисти обладнання.

Контролер перевіряє строк за синхронізованим UTC-часом. Повтор уже відомого `command_id` повертає збережені відповіді, без повторного виконання, навіть після TTL. Сервер приймає запізнілі ACK/Result як свідчення попереднього виконання; надходження відповіді не відновлює доставку.

| Статус | Значення |
| --- | --- |
| queued | Спроби доставки ще не було |
| published | Спробу доставки зафіксовано до мережевого виклику; прийом контролером не доведено |
| acknowledged | Контролер повідомив про прийом; очікуємо результат до окремого deadline 120 с |
| expired | Строк минув до першої спроби доставки |
| cancelled | Доставку припинено до першої спроби |
| result_unknown | Спроба доставки або ACK були; подальших повторів немає, фактичний результат невідомий |
| succeeded / failed | Контролер повідомив фінальний результат |

`published_at` — початок першої спроби, а не доказ отримання MQTT PUBACK. `last_publish_error` показує діагностику транспорту. Після втраченого PUBACK команда може бути вже виконана. При TTL/Stop/відкликанні прав така команда переходить у `result_unknown`. Пізній Result завершує її та закриває відповідний alarm.

## Порядок та Stop

Backend під блокуванням Device виділяє монотонний `control_sequence`, унікальний для пристрою. Контролер атомарно зберігає найбільший прийнятий номер, стан та відповіді до публікації ACK/Result. Нова команда з меншим або рівним номером відхиляється. Відомий `command_id` спочатку перевіряється за ledger та повертає попередній результат. Звичайний reboot не скидає номер.

При створенні Stop backend припиняє доставку старіших queued/published команд. Якщо старий Start уже був у мережі та прийшов після Stop, його відхиляє контролер. Якщо він прийшов раніше, виконання могло початися; мережева зупинка не замінює апаратну аварійну кнопку.

UI дозволяє Stop під час іншого незавершеного або непідтвердженого запиту. Поле HTTP `supersedes_request_id` посилається на цей запит. Якщо повільний Start досягне сервера після Stop, backend збереже його як cancelled, без публікації. Посилання діє лише для того самого Device та автора. Повтор HTTP-запиту повинен зберігати це поле, payload, TTL та request_id. Кнопка Stop використовує типові 30 с, якщо введено некоректний TTL.

Порядок незалежних запитів інших клієнтів визначається сервером. Новий свідомий Start після Stop залишається окремою дозволеною дією.

## Перевірки перед доставкою

Безпосередньо перед кожною спробою backend перечитує активність автора, початкову auth session, поточні права, tenant binding, enabled capability та профіль частоти. Logout/revocation початкової session припиняє майбутню доставку її команд. Refresh тієї самої session не змінює авторство. Уже переданий мережі запит відкликати неможливо; для зупинки потрібен новий Stop.

Зміна частоти вимагає `vfd.control.config.frequency_limits`:

```json
{"frequency_limits": {"min_hz": 20, "max_hz": 50}}
```

Це приклад, не налаштування для довільного обладнання. Потрібні фактичні межі двигуна, частотника та установки. Відсутній/некоректний профіль блокує зміну частоти. Межі перевіряються при POST та повторно перед відправленням. У demo віртуальний VFD має фіксований діапазон 0–50 Гц і перевіряє його також у симуляторі. UI показує налаштований діапазон.

## Оновлення локального demo

1. Збережіть узгоджену резервну копію за [backup-restore-v1.md](backup-restore-v1.md).
2. Зупиніть backend та simulator до зміни схеми. PostgreSQL і Mosquitto залишаються запущеними.
3. Зберіть образ backend, виконайте `alembic upgrade head`, потім `python -m app.demo.seed` у demo Compose. Повторний seed додає лише відсутній профіль віртуального VFD; наявні налаштування не перезаписує.
4. Запустіть backend та simulator нової версії, перебудуйте frontend. Перевірте `/health` → 0.39.0 та поточну міграцію → 0018.
5. Перевірте журнал та фактичний стан пристрою перед новим Start. Міграція припиняє доставку всіх legacy pending команд: усі стають result_unknown. Стара версія записувала спробу після мережевого виклику, тому навіть queued/0 міг бути виконаний перед збоєм процесу.

Новий симулятор не приймає нові v1-команди; лише повторює збережені відповіді legacy ledger. Перехід реального контролера потребує реалізації protocol v2, durable sequence/ledger, синхронізації часу та локальних захистів. Готової firmware в цьому репозиторії ще немає.

Downgrade не відновлює стару чергу. Після відновлення старої БД або заміни контролера потрібне контрольоване узгодження sequence; не скидайте збережений номер контролера для обходу відмов. Старі backup bundles перевіряються за власною версією/міграцією; їх відновлюють з відповідним source archive, після чого окремо оновлюють схему. Restore quarantine позначає published-команди як result_unknown.

## Перевірки та межі готовності

Регресії охоплюють Stop перед старим Start, HTTP Start після Stop, Stop під час MQTT publish, durable attempt при збої процесу, запізнілі ACK/Result, відкликання session/прав/capability, tenant move, зміну профілю частоти, reboot симулятора та downgrade протоколу. Backend CI виконує PostgreSQL/MQTT suite без skips, міграції, live demo і backup/restore. Frontend CI перевіряє контракт API, типи, lint, unit, production build, браузерні та live сценарії.

Це посилює поточний demo, але не завершує виробничу готовність. Device identity/TLS/ACL, реальна firmware, перевірка апаратних interlocks, навантаження та решта [product-readiness-plan-v1.md](product-readiness-plan-v1.md) залишаються окремою роботою. Раніше непідтверджені ручні acceptance-пункти не закриваються цими змінами автоматично.
