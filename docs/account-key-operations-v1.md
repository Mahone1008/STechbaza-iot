# Ключі облікових записів і заводського реєстру

`AUTH_ACCESS_TOKEN_SECRET` підписує короткочасні access JWT. Окремий
`ACCOUNT_KEY_SECRET` захищає TOTP, recovery keys, activation codes, bootstrap
keys і зашифровані MQTT-паролі factory-контролерів. MQTT і TOTP мають окремі
ключі шифрування, похідні від account secret. Заміна JWT secret більше не
змінює ключі цих збережених даних.

## Оновлення наявної установки

Перед першим запуском оновленого backend скопіюйте **попереднє значення**
`AUTH_ACCESS_TOKEN_SECRET` у `ACCOUNT_KEY_SECRET`. Для demo використовуйте
`DEMO_ACCOUNT_KEY_SECRET` зі значенням попереднього `DEMO_JWT_SECRET` у
наявному `.env.demo`. Не генеруйте новий файл credentials поверх старого.
Це разове перенесення зберігає чинні recovery/activation/bootstrap keys і TOTP
без зміни БД чи повторної видачі комплектів. Після цього JWT secret можна
змінювати незалежно; account secret залишається незмінним.

Compose вимагає явного account secret. Прямий Python startup із нестандартним
JWT secret без `ACCOUNT_KEY_SECRET` також завершується з поясненням міграції.
Локальний development fallback збережено лише для попереднього стандартного
development secret. Для нової установки потрібен окремий випадковий secret
щонайменше з 32 символів.

## Планова ротація account secret

1. Збережіть захищену резервну копію БД та чинних ключів.
2. Запишіть новий випадковий ключ у `ACCOUNT_KEY_SECRET` (для demo —
   `DEMO_ACCOUNT_KEY_SECRET`). Попередній додайте до `ACCOUNT_KEY_PREVIOUS_SECRETS`:
   це JSON-масив рядків, максимум три старі ключі, без повторів.
3. Передайте однаковий набір усім API/workers та перезапустіть їх разом.
   Під час переходу не залишайте процеси, що знають лише старий ключ:
   вони не зможуть читати щойно створені секрети.
4. Перевірте вхід із TOTP, recovery, claim і bootstrap на окремих тестових
   облікових записах/контролерах. Не витрачайте recovery/activation key покупця
   для перевірки установки.

Чинні MQTT-паролі читаються через збережені попередні account keys, але
саме читання не перешифровує їх. Перед вилученням старого account key
виконайте планову ротацію доступу кожного залежного контролера за
[процедурою етапу 2](stage2-acceptance.md#6-ключі-перепродаж-і-повернення):
безпечна зупинка, новий пароль, ACK брокера та повторне підключення.
Для відкликаних credentials серверний revoke не потребує розшифрування;
архівні ciphertext усе одно потребують старого ключа для читання backup.

Успішна перевірка TOTP повторно шифрує його поточним ключем; успішний bootstrap
перезаписує digest поточним ключем. Recovery key замінюється після recovery
або явної ротації, activation code витрачається при claim. Нові дані одразу
використовують поточний ключ.

**Не вилучайте старий ключ лише за календарною датою.** Невикористані коди
активації, офлайн-контролери й recovery keys досі можуть залежати від нього.
Наявні digest не містять ідентифікатора ключа; без оригінального коду їх
неможливо перерахувати. Вилучення потребує підтвердженої заміни/витрачання
всіх залежних секретів. Автоматичної масової міграції офлайн-комплектів немає.
Недоступний ключ TOTP дає контрольований HTTP 503, а не вимикає MFA.

## Резервне копіювання

Зберігайте поточний і збережені попередні account keys разом із захищеною
конфігурацією резервної копії, окремо від публічних артефактів. БД без цих
ключів не дозволить відновити TOTP/MQTT-паролі або перевірити видані opaque keys.
Для старого backup без account setting спочатку перенесіть його **старий JWT
secret** за процедурою вище; не підставляйте JWT secret нової установки.
Інші кроки: [backup/restore](backup-restore-v1.md).
