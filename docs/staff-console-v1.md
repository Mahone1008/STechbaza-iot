# Закритий кабінет адміністратора та сервісу

Версія backend **0.52.0**, міграція **20261007_0029**. Клієнтська реєстрація залишається; Authenticator для клієнта добровільний. Для персоналу у закритому застосунку він обов’язковий. [Розгортання через VPN](staff-pilot-deployment.md).

## Три кабінети

| Кому | Оформлення | Що доступно |
|---|---|---|
| Клієнт | Бірюзовий | Власні організації, об’єкти, обладнання, учасники в межах ролі; особиста безпека |
| Сервіс, `service_admin` | Синій | Призначені організації й конкретні об’єкти, показники, аварії, команди, розклади, обслуговування; особиста безпека |
| Головний адміністратор, `superadmin` | Графіт і мідь | Усі користувачі, глобальні ролі, доступ, організації й об’єкти, обладнання, виробничий реєстр, журнал дій, стан сервісів |

Роль сервісу сама по собі не відкриває всіх клієнтів. Потрібне членство в організації, дозволені об’єкти й незавершений строк доступу. Глобальна роль користувача та роль учасника організації змінюються окремо.

Це два незалежні серверні застосунки: `app.main:app` з `APP_PLANE=customer` і `app.staff_main:app` з `APP_PLANE=staff`. Вони мають окремі JWT secrets, audiences та refresh cookies. У production також окремі ролі PostgreSQL. Клієнтський API не монтує `/staff/*` і `/factory/*`; закритий API не приймає реєстрацію покупців або активацію контролера. Службовий MQTT клієнт лише публікує команди; телеметрію, результати й календар обробляє один клієнтський worker.

## Оновлення Windows і очищення старих прикладів

Запустіть Docker Desktop та дочекайтеся готовності engine. Зупиніть обидва старі вікна `npm run dev` через Ctrl+C. В окремому PowerShell:

```powershell
Set-Location 'C:\Users\seraf\Documents\TechBaza\techbaza-iot'
git status --short
```

Якщо є ваші незбережені зміни, збережіть їх перед `git pull`. Два автоматично згенеровані frontend-файли можна прибрати в stash:

```powershell
git stash push -m 'before-staff-console' -- frontend/next-env.d.ts frontend/src/lib/api/schema.d.ts
git pull --ff-only origin main
if ($LASTEXITCODE -ne 0) { throw 'Оновлення зупинено' }
```

Спочатку переконайтеся, що `.env.demo` зберігає чинний `DEMO_ACCOUNT_KEY_SECRET`. Не створюйте `.env.demo` заново: це змінило б ключі. [Порядок перенесення старого secret](account-key-operations-v1.md).

Запуск **з очисткою всіх наявних demo-акаунтів**, включно з особистими тестовими поштовими адресами:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-staff-demo.ps1 -ResetExisting
```

Скрипт створить `.env.staff` один раз, збере сервер, застосує міграцію, покаже перелік акаунтів для очищення, зупинить writers, збереже PostgreSQL backup у `.local/demo-reset/<дата>/before-reset.dump` і запустить два API. Очистка дозволена тільки в базі `techbaza_demo` з demo-прапором. Збереження backup є обов’язковою частиною скрипту; за його помилки очистка не почнеться.

Що очиститься:

- Authenticator, ключі відновлення, email/activation links, login throttles та відкриті сесії;
- усі об’єкти й контролери, конфігурації, паспорти обладнання, телеметрія, аварії, команди, розклади та їх історія;
- заводські картки/QR й bootstrap credentials прикладів.

Що збережеться: логіни, password hashes, статус акаунта, глобальні та організаційні ролі, обмеження доступу й строки. Порожні організації та їх членства залишаться. Якщо членство було обмежене видаленими об’єктами, воно **не перетвориться** на доступ до всіх нових об’єктів: призначте нові об’єкти явно в панелі. Збережений файл `.local/demo-accounts/accounts.json` лишається чинним; паролі не генеруються заново.

Якщо є робочі мережеві ключі контролерів, gateway повинен підтвердити їх відкликання. Без відповіді очистка БД скасується. Симулятор після очистки залишається зупиненим, щоб не відтворювати видалені приклади. Для повторного запуску **без нової очистки**:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-staff-demo.ps1
```

Окремий попередній перегляд очистки:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\reset-demo-review.ps1 -AllExisting
```

Якщо Windows показує `PSSecurityException` або «выполнение сценариев отключено», файл ще не запустився: очистка не відбулася. Наведений `Bypass` діє лише в окремому процесі PowerShell і не змінює постійну політику Windows.

## Запуск двох сайтів

У першому PowerShell, для клієнтів:

```powershell
Set-Location 'C:\Users\seraf\Documents\TechBaza\techbaza-iot\frontend'
npm.cmd ci
if ($LASTEXITCODE -ne 0) { throw 'Не встановлено залежності' }
$env:NEXT_PUBLIC_PORTAL_MODE = 'customer'
$env:NEXT_PUBLIC_API_BASE_URL = 'http://127.0.0.1:8001'
$env:NEXT_PUBLIC_CUSTOMER_URL = 'http://127.0.0.1:3000'
npm.cmd run dev -- --port 3000
```

У другому PowerShell, для персоналу:

```powershell
Set-Location 'C:\Users\seraf\Documents\TechBaza\techbaza-iot\frontend'
$env:NEXT_PUBLIC_PORTAL_MODE = 'staff'
$env:NEXT_PUBLIC_API_BASE_URL = 'http://127.0.0.1:8002'
$env:NEXT_PUBLIC_CUSTOMER_URL = 'http://127.0.0.1:3000'
npm.cmd run dev -- --port 3001
```

Клієнт: <http://127.0.0.1:3000>. Адміністратор і сервіс: <http://127.0.0.1:3001>. Збираються окремі каталоги `.next` та `.next-staff`. NEXT_PUBLIC налаштування задаються **до** запуску/збірки. Звичайний demo без overlay лишається сумісним зі старими локальними перевірками; для ізоляції використовуйте цей порядок.

| Наявний demo-акаунт | Сайт для входу |
|---|---|
| `owner@kerumo-demo.example.com`, `admin@kerumo-demo.example.com`, `operator`, `viewer`, `other`, `new` | Клієнтський, `3000` |
| `service@kerumo-demo.example.com`, `superadmin@kerumo-demo.example.com` | Службовий, `3001` |

`admin` є адміністратором організації, а не головним адміністратором платформи. Вхід служби/головного адміністратора на клієнтському сайті відхиляється навіть із правильним паролем; загальне повідомлення не розкриває роль чужого акаунта. Повторна реєстрація зайнятого email неможлива, незалежно від його ролі. Паролі особистих акаунтів зберігаються як хеші; `.local/demo-accounts/accounts.json` містить лише початкові паролі восьми demo-акаунтів. Після особистої зміни пароля файл не оновлюється.

## Фізичний V3 після очистки

`-ResetExisting` видаляє також серверний об'єкт і пристрій фізичного V3. Прошивка ESP32, `.env.v3`, сертифікати й мережеві налаштування старого V3 gateway зберігаються. Власник отримує доступ через організацію; його email не записано в прошивці.

[Відновлення V3 у кабінеті owner](v3-restore-after-reset.md) додає назад лише фізичний SU600 до наявної «DEMO: клієнт A», запускає його gateway з чинними ключами й залишає керування вимкненим. Симулятор і решта видалених прикладів не відновлюються. Це серверна реєстрація стенда, не нове фізичне приймання firmware.

## Перша перевірка після очистки

1. На `3001/login` увійдіть `superadmin@kerumo-demo.example.com` з паролем із `.local/demo-accounts/accounts.json`. Старий Authenticator не потрібен: його прив’язку скинуто.
2. Кабінет покаже пропозицію налаштувати захист. Відкрийте «Моя безпека», збережіть новий ключ відновлення, додайте новий TOTP запис у застосунок і підтвердьте свіжим шестизначним кодом. Видалення запису в телефоні саме по собі не вимикає MFA на сервері.
3. Поверніться до службового кабінету. Має бути графітове оформлення, меню «Користувачі», «Організації», «Обладнання», «Виробництво», «Журнал дій», «Стан сервісів». Лічильники обладнання й об’єктів після очистки нульові.
4. Вийдіть і увійдіть знову з паролем та **новим** кодом. Без коду має бути зрозуміле повідомлення про двоетапний вхід; до операцій доступ закрито.

## Користувачі, ролі та захист

1. «Користувачі»: знайдіть email. Для нової людини спочатку звичайна реєстрація з підтвердженням пошти на клієнтському сайті; потім тут можна призначити роль сервісу/адміністратора.
2. «Змінити»: ім’я, активність, глобальна роль. Для підтвердження потрібні причина, **ваш** поточний пароль і свіжий код. Пароль цільового користувача не змінюється і не показується.
3. Після зміни ролі або блокування перевірте стару вкладку користувача: її сесію відкликано. Повторний вхід має відповідати новій ролі. `user` входить лише на `3000`, `service_admin`/`superadmin` лише на `3001`.
4. «Сесії»: перегляньте час, IP та browser information; завершення всіх сесій потребує підтвердження. У цільового користувача наступний приватний запит має вимагати входу.
5. «Скинути захист»: якщо людина втратила Authenticator, відкличте MFA. Прапор також скидає ключ відновлення. Старий пароль і права зберігаються; сесії відкликаються. Персоналу при новому вході потрібно знову прив’язати Authenticator.
6. Спроба заблокувати/понизити себе як головного адміністратора, залишити платформу без активного головного адміністратора або організацію без доступного власника має бути відхилена.

Повторне використання одного TOTP для двох чутливих дій відхиляється. Дочекайтеся наступного коду. Редагування застарілої версії запису не перезаписує чужу зміну: оновіть список і повторіть.

## Організації, об’єкти й сервісний доступ

1. «Організації»: створіть тестову організацію, відкрийте її, створіть об’єкт із назвою й кодом.
2. «Учасники»: додайте існуючий підтверджений email або надішліть запрошення новій людині. Роль, строк і дозволені об’єкти задаються явно.
3. Для сервісного акаунта поставте «Лише обрані об’єкти» і виберіть один об’єкт. Порожній вибір не можна підтвердити. Це захищає від випадкового доступу до всієї організації.
4. Увійдіть сервісом у приватному вікні на `3001`: синє оформлення; немає користувачів усієї платформи, виробництва, глобального журналу й моніторингу. Видно лише призначені об’єкти/обладнання. Інша організація й об’єкт поза scope недоступні також через пряме посилання.
5. Змініть строк/відкличте членство: сервіс має втратити доступ на наступному запиті. Його особистий акаунт продовжує існувати.
6. Перейменуйте порожній об’єкт, змініть timezone, видаліть його з підтвердженням. Об’єкт з обладнанням видалити не можна. Timezone зайнятого об’єкта не змінюється, щоб не зсунути календарні запуски.
7. Архівування організації можливе після перенесення/виведення її обладнання; видалення лише порожньої архівної організації. Операції з фізичним обладнанням залишаються у його спеціальному майстрі та не замінюються видаленням рядка БД.

## Виробництво й обладнання

«Виробництво» доступне лише головному адміністратору у приватному застосунку. Тут готують контролер, картку активації, постачання та переглядають заводський аудит. Картку отримує покупець у закритій упаковці. QR посилається на **клієнтський** сайт, а не службовий. Реєстрація покупця не дає виробничих прав.

Перевірте створення тестової картки й відкриття її QR у клієнтському приватному вікні. Майстер має запропонувати вхід/реєстрацію, після них повернути до активації, вибору організації, об’єкта й підтримуваного профілю частотника. [Повний фізичний сценарій](stage2-acceptance.md); ця панель не змінює firmware та не оголошує неперевірені драйвери доступними.

«Обладнання»: пошук контролера/організації/об’єкта, фільтр без зв’язку, перехід на панель пристрою. Показники, команди, розклади, журнал, зміна/передача обладнання використовують наявні backend перевірки та фактичні capabilities. У сервісу створене доручення календаря виконується єдиним worker, доки чинні його права й scope.

## Журнал і стан сервісів

«Журнал дій»: хто, коли, IP, результат, причина змін та номер запиту. Фільтр виду зміни/невдалих запитів, пагінація, завантаження **поточної сторінки** JSON. Старі події до міграції не відтворюються. Чутливі адміністративні зміни записуються в тій самій транзакції; якщо запис аудиту не вдався, зміна скасовується. HTTP записи для інших операцій записуються окремо; їх відмова видима в structured logs.

«Стан сервісів»: доступність і розмір БД, з’єднання, пам’ять/диск контейнера службового API, MQTT зв’язок worker, стан обробки команд/аварій та HTTP лічильники клієнтського API. Лічильники починаються від запуску процесу. Це не весь трафік Linux-сервера і не довгострокова система метрик.

Для перевірки недоступного worker зупиніть **тільки у тестовому стенді** клієнтський backend: індикатор має показати «Немає відповіді», а не попередній успішний стан. Після запуску й оновлення показники повернуться. Публічний `/_internal/status` без секрету повертає 404.

## Автоматичні перевірки та межі

- Backend: базовий `python -m app.tools.backend_check` (PostgreSQL + MQTT), окремо `APP_PLANE=staff` suite `tests/staff_checks.py`.
- Frontend: `npm run typecheck`, `lint`, `format:check`, `test:unit`, клієнтський `build`/`test:browser`, службовий `build:staff`/`check:budget:staff`/`test:staff`.
- CI перевіряє private RBAC, MFA gate, scope, відкликання sessions, атомарний audit, захист password/security/session рядків через PostgreSQL RLS і виконання сервісного календаря без доступу worker до staff password hash.

Нова панель не дає web-shell, Docker socket, доступ до приватних secrets або довільні SQL-команди. Доступ до Linux-сервера, VPN membership, backups, TLS, SMTP й host monitoring налаштовуються в окремому deployment runbook.
