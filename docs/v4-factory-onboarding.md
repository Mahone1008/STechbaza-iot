# V4: заводська активація через 4G

Реалізація: backend 0.55.0, міграція `20261012_0031`, firmware 0.12.0.
Заводська активація тепер працює через PPP/HTTPS із тим самим контрактом,
що й Wi-Fi. Це програмна реалізація; фізичне приймання ESP32-S3/A7670E/SU600
потрібно виконати після завантаження. Успішний host test не є таким прийманням.
[Повний порядок: виробник → клієнт → монтажник](v4-full-control-onboarding.md).
У 0.55.0 покупець лише активує обладнання, виробник може заздалегідь
підготувати паспорт, а службовий монтажник завершує чотири кроки перевірки.

## Що отримує покупець

На контролері — один постійний QR із публічним посиланням `/connect/{id}`
і серійний номер. На окремій закритій картці — серійний номер і одноразовий
пароль активації. QR не містить цього пароля, заводського ключа чи MQTT credentials.
Окремий пароль локального налаштування доступний у технічному розділі комплекту.
Він відкриває лише локальну мережу для перевірки обладнання, не особистий акаунт.

1. Сканує QR, входить у свій акаунт або підтверджує пошту й створює його.
2. Вводить пароль активації й назву об'єкта або обирає наявний. Типовий
   «Мій особистий кабінет» створюється один раз і використовується повторно.
   Назва контролера й організація доступні в додаткових параметрах.
   Повторний QR відкриває вже прив'язаний пристрій, не створює новий.
3. Для V4 подає живлення на контролер і модем із SIM та чекає зв'язку.
   Домашній Wi-Fi не потрібний. SIM/APN готує виробник або монтажник.
4. Чекає автоматичного оновлення готовності; за потреби запрошує існуючого
   сервісного монтажника лише до цього об'єкта. Паспорт, робочі межі,
   локальне підтвердження й дозвіл використання виконує виробник або
   монтажник у службовому кабінеті. Активація не запускає двигун.

Сайт окремо показує власника, автентифікований контакт плати та свіжі показання.
Сам bootstrap contact не означає зв'язок із частотником або дозвіл RUN.
Виробник або монтажник до першої конфігурації може виправити помилку початкового паспорта;
після налаштування діють звичайні захищені операції заміни.
Серія SU600 не дозволяє керувати довільною моделлю: поточний перевірений профіль
прив'язаний до `SU600A-5RG1-B`. Не підміняйте реальну модель для розблокування.

## Що один раз робить виробник

1. У службовому кабінеті реєструє контролер із типом мережі **4G (LTE)**,
   серійним номером і протоколом заводської перевірки. Для комплекту з
   частотником готує паспорт фактичного SU600A-5RG1-B, дані двигуна й робочі
   межі; для окремого контролера залишає цю роботу монтажнику.
2. Завантажує приватний `factory-{serial}.json`, друкує публічний QR і закриту
   картку. JSON із bootstrap key зберігає у виробника; покупцю його не передають.
3. Готує стабільний HTTPS API і managed MQTT із чинними сертифікатами.
4. Генерує окремий скетч і завантажує його в відповідну ESP32-S3.
5. Перевіряє холодний старт від окремого живлення та показання на новій картці.

Для раніше створеного контролера тип мережі можна уточнити у заводському реєстрі
до видачі credentials/конфігурації. Якщо перший автентифікований контакт мав
інший тип мережі, дозволено виправити лише на тип, який підтвердила плата.
Контролер, QR, власник і ключ не змінюються; дія записується в аудит.
Збережений JSON — знімок попередніх даних: явний `--transport lte` у генераторі
потрібний для старого комплекту після уточнення реєстру. Сервер усе одно перевіряє
тип мережі перед видачею MQTT credentials.

```powershell
Set-Location 'C:\Users\seraf\Documents\TechBaza\techbaza-iot'

# Docker Desktop має працювати; якщо образу генератора ще немає:
docker build --tag techbaza-demo-backend:local .\backend
if ($LASTEXITCODE -ne 0) { throw 'Не створено образ генератора' }

# Типово Full; шляхи до JSON та CA скрипт запитає інтерактивно.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\prepare-factory-v4.ps1
if ($LASTEXITCODE -ne 0) { throw 'Комплект прошивки не підготовлено' }
```

Команда з явними параметрами для тієї самої підготовки:

```powershell
Set-Location 'C:\Users\seraf\Documents\TechBaza\techbaza-iot'

# Адреси й CA мають відповідати вашому розгорнутому серверу.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\prepare-factory-v4.ps1 `
  -KitPath 'C:\private\factory-566787.json' `
  -ApiUrl 'https://app.example.com' `
  -CaPath 'C:\private\api-ca.pem' `
  -MqttCaPath 'C:\private\mqtt-ca.crt' `
  -Apn 'internet' `
  -ControlMode Full
if ($LASTEXITCODE -ne 0) { throw 'Комплект прошивки не підготовлено' }
```

Скрипт друкує шлях до нового скетча в `.local/factory-v4/{random}/kerumo_v3`.
В Arduino IDE відкрийте **саме його** `kerumo_v3.ino` та завантажте в плату.
Стандартний порт UART2: TX4/RX5; SU600: UART1 TX17/RX18.
Старі `*.local.h`, статичний UID/MQTT пароль і manifest не копіюються.
Існуючий каталог виводу не перезаписується. Секрети у stdout не друкуються.

Генератор типово працює через локальний Docker-образ без мережі; Python
у Windows не потрібний. `-PythonCommand` лишається явною альтернативою.
`Full` — типова підтримка всіх режимів керування в сумісній прошивці;
сервер видає окремий ревізований дозвіл лише після перевірки монтажником.
`ReadOnly` — явно обмежений комплект для спостереження; `Bench`, `Extended`,
`Remote` лишаються сумісними варіантами генератора. Дозвіл і режим використання
сумісної Full-плати змінюються без перепрошивки. Кеш не відновлює дозвіл
після boot. Нова команда START потрібна завжди; reboot, claim,
локальне відновлення дозволу і повернення мережі не є START.

## Сервер

Публічний HTTPS customer API вже маршрутизує `/api/v1/bootstrap/*` через
[pilot Caddy](../infrastructure/staff/Caddyfile). Приватні заводські/службові
маршрути лишаються закритими. Для managed MQTT використовуйте
[factory pilot overlay](../compose.factory.pilot.yml) разом із
[pilot deployment](staff-pilot-deployment.md). Шлюз має стабільну публічну IPv4,
TLS-порт 8884 і окремий внутрішній адміністративний порт 1884.
Адміністративний порт не публікується на хості.

```powershell
# На хості сервера. PUBLIC_SERVER_IP замініть його реальною стабільною IPv4.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\prepare-controllers.ps1 -HostIp 'PUBLIC_SERVER_IP'
docker compose --env-file .env.pilot --env-file .env.controllers -f compose.pilot.yml -f compose.factory.pilot.yml config --quiet
docker compose --env-file .env.pilot --env-file .env.controllers -f compose.pilot.yml -f compose.factory.pilot.yml up -d --wait controller-gateway backend staff-backend
```

Це додаток до вже налаштованого pilot, не заміна його початкового встановлення,
міграцій, DB roles і SMTP. `.local/controllers-ca.crt` — CA для MQTT.
Для запрошення монтажника потрібен налаштований `STAFF_PUBLIC_URL`:
посилання відкриває службовий вхід фахівця через його VPN, а не клієнтську реєстрацію.
Для HTTPS API використовується CA його справжнього сертифіката; він може відрізнятися.
`127.0.0.1`, LAN-IP ноутбука й сайт лише на localhost не доступні модему через SIM.
Годинний Pinggy endpoint не є постійним заводським endpoint.

Приватний ключ CA зберігається окремо у `.local/controller-signing` і не
монтується у працюючий брокер та не додається до заводського комплекту.
Зробіть окрему захищену резервну копію цієї папки. Серверний сертифікат
діє 180 днів; його планове продовження зберігає CA, QR і паролі пристроїв:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\prepare-controllers.ps1 -HostIp 'PUBLIC_SERVER_IP' -RenewTls
docker compose --env-file .env.pilot --env-file .env.controllers -f compose.pilot.yml -f compose.factory.pilot.yml restart controller-gateway
```

Після такого продовження прошивки не змінюють. Заміна самого CA або публічної
IPv4 — окрема контрольована міграція довіри, не автоматична зміна endpoint.
Для старого шлюзу без збереженого ключа CA продовження відмовляє без заміни
ключів; потрібна його відповідна приватна резервна копія.

## Існуючий V4 і перенесення власника

Статичний стенд `KERUMO-V3-SU600-001` не стає factory controller після QR.
Перед завантаженням зупиніть/заблокуйте стару установку. Потрібні її приватний
заводський комплект і одноразова заміна прошивки на factory LTE скетч.
Новий managed UID належить новій картці; стара історія лишається старій картці.
Немає автоматичного переведення чужої історії або повторного використання legacy credentials.

Наступна передача власника використовує чинний захищений release: STOP,
перевірка доступу, відкликання credentials із підтвердженням брокера,
новий пароль активації й нове покоління Device. Публічний QR лишається тим самим.
Прошивка отримує новий UID/manifest через bootstrap; старий кеш не відновлює доступ.
Заводський шаблон старої установки очищується при передачі; новий монтажник
має звірити фактичне обладнання й підготувати його паспорт. Ротація мережевого
ключа також скасовує серверний дозвіл: потрібне повторне місцеве підтвердження
та службове введення в роботу, без повторного Serial ARM для Full-плати.

## Фізичне приймання

Перевірте на реальній платі: холодний старт без USB; SIM/APN→PPP→UTC→HTTPS→MQTT;
відсутність зв'язку до правильного ключа/типу мережі; QR і одноразову активацію;
manifest→локальний STOP→свіжий readback; втрату 4G і повернення без самопуску;
відкликання/передачу без доступу попереднього власника. Записуйте версії,
умови й boot logs без приватних ключів. Host та browser tests цього не замінюють.
