# V3 / SU600 — тривалі випробування з двигуном

Ця інструкція описує **ручний ARM**. У firmware 0.8.0 є окремий [режим без повторного Serial ARM](v3-remote-operation.md), вимкнений за замовчуванням. Новий режим не означає автоматичний пуск двигуна.

Поточне оновлення — **0.6.0**: [таймери/програми та порядок оновлення
backend → сайт → скетч](control-programs-v1.md). Наведені нижче 0.2.x
результати є доказами своїх revisions. Базова фізична підготовка й ARM TEST
залишаються чинними; приймання програм виконується окремо.

Firmware **0.2.1**, 30.09.2026. Режим для випробувань під наглядом без
програмного ліміту тривалості RUN. На V3 через Wi-Fi підтверджено базове
керування, повторний START та зупинки при втраті gateway, команді DISARM
і знеструмленні ESP32. [Досьє з доказами й межами приймання](dossier-v3-su600-control-bench.md).
Окрема втрата Wi-Fi, тривала стабільність і всі відмови ще не прийняті.

Базові перевірки 0.2.0: native C++ suite з Address/UndefinedBehaviorSanitizer
(LeakSanitizer недоступний у цьому середовищі), 19 backend unit tests,
92 frontend unit tests, TypeScript, ESLint та production build сайту.
Варіант extended test 0.2.0 зібрано для ESP32-S3 N16R8 / USB-UART на core 3.3.1:
1 028 399 байтів flash, 50 184 байти статичних RAM-даних.
Браузерні regression tests додано, але локальний Chromium не запускається через
системну заборону socket; цей прогін не зарахований. Це не перевірка фізичного двигуна.

У 0.2.1 виправлено розбір F5.00: на фізичному SU600A панель показує `1001`,
а Modbus повертає `0x1001` (десяткове сире значення `4097`). Кожен розряд
панелі займає чотири біти регістра. У 0.2.0 перевірка помилково застосовувала
десяткові `/100` і `%10`, тому відхиляла цей коректний набір налаштувань.
Serial тепер показує `F5.00=1001 (raw=4097)`; числові регістри на кшталт
F6.02 не переводяться в цей формат. Налаштування самого VFD прошивка не змінює.

Для 0.2.1 повторно пройдено native C++ suite з Address/UndefinedBehaviorSanitizer
(без LeakSanitizer), включно з усіма 65 536 можливими словами F5.00, ARM без
запису команд у VFD, відмовою для режиму продовження RUN при втраті зв'язку,
START/STOP та роботою довше 60 с. Збірка extended test для ESP32-S3 N16R8 /
USB-UART успішна: 1 028 359 байтів flash, 50 184 байти статичних RAM-даних.
Історичний CI 30.09 після виправлення застарілих browser expectations:
92 unit / 160 mocked / 10 live та 44 повтори PASS; [точні revisions і межі](audit-2026-09-30.md).

Ці автоматичні перевірки самі по собі не підтверджують фізичний пуск чи зупинку;
подальші результати оператора наведені в досьє та таблиці приймання нижче.

## Поведінка

- `ARM SU600 TEST` дозволяє повторювати частота → START → STOP без нового ARM
  після штатного STOP. Автостоп 60 с у цьому сеансі вимкнений.
- DISARM, втрата мережі, помилка VFD/RS485, невідомий результат, невідповідний
  профіль або збій сховища знімають дозвіл. Після них потрібний новий місцевий ARM.
- Перезапуск не відновлює дозвіл чи START. NVS і послідовність команд зберігаються.
- Старий `ARM SU600` лишає попередній 60-секундний тест без двигуна.
- Панель та перша сторінка журналу типово оновлюються кожні 5 с, історія
  телеметрії — кожні 60 с. Старі сторінки команд не пересуваються.
- Діагностика контролера пояснює відсутність локального дозволу до надсилання
  START/частоти. STOP лишається доступним без ARM і під час оновлення панелі.
- TTL 30 с — строк початку виконання доставленої команди, не затримка старту
  і не тривалість роботи. Уже виконаний START не припиняється через завершення TTL.

Прихована вкладка, ручний режим оновлення, затримки після помилок, TLS,
авторизація та захист від повторних/прострочених команд зберігаються.

## Обладнання на фото та підготовка

| Обладнання | Дані шильдика користувача |
|---|---|
| VFD | SUSWE SU600A-5R5G1-B, 5,5 кВт; вхід 1×220 В, вихід 3×0–380 В, 13 А |
| Двигун | АИР56А4У3, 3 фази, 120 Вт, 50 Гц, 1350 об/хв, S1 |
| З'єднання / струм | Δ/Y 220/380 В; 0,76/0,44 А відповідно |

На фото клемна коробка відкрита. Перед пуском електрик має перевірити
з'єднання для вибраної напруги, PE, кріплення двигуна, кабелю, захист вала
та незалежну зупинку; клемну коробку закрити. Фото не підтверджують ці перевірки.

**Захист великого VFD не можна автоматично вважати захистом цього мотора.**
У посібнику SU600 V1.0 мінімум F5.01 становить 30% струму приводу: для 13 А
це 3,9 А, значно більше за 0,44 А мотора. Потрібен перевірений окремий захист,
сумісний із виходом VFD, або відповідний привід; звірити діапазони саме ревізії SU600A.
Показання струму з кроком 0,1 А не замінюють моторний захист.

F4.00–F4.04 звірити з мотором. 0,12 кВт та 0,44 А — дані шильдика, а не
гарантія точності налаштування цієї ревізії; не округляти навмання і не підставляти
5,5 кВт / 13 А. Firmware ці параметри не записує і підбір моторного захисту не перевіряє.
Межі команд лишаються 0–50 Гц. 0 Гц не замінює STOP; S1 не означає, що будь-яка
мала частота допустима для тривалої роботи під навантаженням.

## Додаткові перевірки ARM TEST

Базовий профіль F0/F6 із [попередньої інструкції](v3-su600-bench.md) зберігається.
Додатково firmware читає, але не змінює:

| Параметр | Умова |
|---|---|
| F6.02 | 5,0–10,0 с; для стенду обрати 5,0 с, у Serial сире значення 50 |
| F5.00 | Розряди як на панелі: одиниці — 1; сотні — 0 або 2; десятки й тисячі — 0 або 1. Перевіряється упакований регістр, наприклад `1001` = `0x1001` |
| F4.08 | 0: автоматичне скидання аварій вимкнене |
| Стан | STOP, вихід 0 Гц, помилка 0, коректний час і сховище |

F6.02=0 вимикає таймаут RS485. Не переписувати інші розряди F5.00 навмання.
Показане користувачем `F5.00=1001` уже задає зупинку на вибігу при втраті
зв'язку та увімкнений прапорець захисту перевантаження. Змінювати його для
обходу помилки 0.2.0 не потрібно; потрібне оновлення firmware до 0.2.1.
Ці перевірки не підтверджують електробезпеку чи струмовий захист мотора.
До тривалого прогону перевірити, що SU600 сам зупиняється при зникненні живлення ESP32:
вимкнений контролер не може відправити STOP. Вебкнопка не є аварійним вимикачем.

Джерело параметрів: [посібник SUSWE SU-600 V1.0, групи F4–F6](https://manuals.plus/m/2881c9389f771d9d5ea8d704f0d72c851a51e1b61809e3e1ce2241aa2efca88b).

## Оновлення Windows / Arduino

Якщо 0.2.0 уже завантажено і backend показує `test_session: extended`, для
виправлення F5.00 достатньо `git pull --ff-only` та повторного завантаження
скетчу через USB. Перебудова backend і повторне ввімкнення профілю не потрібні.
У наявному `config.local.h` обидва прапорці керування лишаються `true`;
`config.example.h` є шаблоном і не вмикає функції у вже створеному local-файлі.

Зупинити двигун. Зберегти попередню папку скетчу окремо з локальною
конфігурацією; паролі не публікувати. Зупинити `npm run dev` через Ctrl+C.
У PowerShell:

```powershell
Set-Location "C:\Users\seraf\Documents\TechBaza\techbaza-iot"
git pull --ff-only
```

При конфлікті локальних змін зберегти повідомлення; не виконувати `reset --hard`.
Після успішного pull:

```powershell
docker compose -p techbaza-demo --env-file .env.demo -f compose.demo.yml up -d --build --no-deps backend
```

Після готовності backend та фізичної підготовки:

```powershell
docker compose -p techbaza-demo --env-file .env.demo -f compose.demo.yml exec -T backend python -m app.bench.su600 --enable-control-extended-test
```

Очікуються `control_enabled: true`, `test_session: extended`. Ідентичності та
історія зберігаються; невідомий змінений профіль не перезаписується.
Повторно запускати `prepare-v3.ps1` не потрібно: він вимикає керування.

У **наявному** `firmware/kerumo_v3/config.local.h` змінити/додати:

```cpp
#define KERUMO_ENABLE_CONTROL true
#define KERUMO_ENABLE_EXTENDED_TEST true
```

Інші налаштування лишити. В Arduino IDE відкрити цілий `kerumo_v3.ino`,
завантажити **через USB** з попередніми налаштуваннями ESP32-S3 N16R8.
`Erase All Flash Before Sketch Upload: Disabled`. Serial Monitor: **115200, Newline**.

Після `storage=OK`, `MQTT CONNECTED / TLS`, `TEST: ... ready=1` та фізичної
підготовки надіслати **в Serial Monitor**:

```text
ARM SU600 TEST
```

Очікується `ARMED: SU600 EXTENDED TEST, no duration cap; normal STOP keeps permission`.
Двигун сам не запускається. При `ARM TEST DENIED` перевірити показані умови;
не обходити відмову старим ARM при підключеному двигуні.

Перший крок після виправлення F5.00 — перевірка дозволу без START:
банер `KERUMO V3 test 0.2.1`, `storage=OK`, MQTT/TLS, `F6.02=50`,
`F5.00=1001 (raw=4097)`, `ready=1`, потім `ARM SU600 TEST` і
`session=EXTENDED ... armed=1` у відповідних рядках Serial. Вихід залишається
0 Гц; це ще не приймання фізичного START/STOP або захисту від втрати зв'язку.

В окремому PowerShell:

```powershell
Set-Location "C:\Users\seraf\Documents\TechBaza\techbaza-iot\frontend"
npm.cmd run dev
```

Відкрити **http://127.0.0.1:3000**, автооновлення «Панель: 5 с».
При зміні IP/сертифіката або зупиненому gateway спочатку відновити MQTT/TLS
за базовою інструкцією; перевірку сертифіката не обходити.

## Приймання оператором

Робочі частоти і допустиму тривалість для підключеного мотора/навантаження
погодити з фахівцем. Відсутність таймера не означає автоматичний дозвіл на безперервний прогін.

Статуси станом на 30.09.2026; точні події та вкладення — у
[досьє керування](dossier-v3-su600-control-bench.md).

| Тест | Очікування | Зафіксований результат |
|---|---|---|
| Уставка в STOP | Свіжі RUN=Ні, вихід=0; уставка сама не запускає мотор | Підтверджено: задано 20 Гц, вихід 0, RUN «Ні» |
| START → ручний STOP | STOP під RUN; вихід=0 і зупинка вала | Базовий цикл прийнято; ACK/Result, телеметрія, журнал і підтвердження оператора |
| Повторний START | Штатний STOP зберіг ARM; новий запуск лише командою | Підтверджено повторний START 12:44:39 і STOP 12:45:39 |
| Частота під RUN | Уставка/вихід, результат і журнал узгоджені | Підтверджено 20 → 30 Гц; точність вимірювання струму окремо не прийнята |
| Понад 60 с | Немає `bench_timer`; зупинка по STOP або захисній події | EXTENDED підтверджено; безперервний хронометрований і тривалий прогін ще відкриті |
| F5 браузера | Сесія відновлюється; повторного START немає | Сесію перевірено в етапі читання; окремий F5 під RUN не зафіксований |
| Gateway | Зупинка, `network_lost`, ARM=0; reconnect без самозапуску | Прийнято: фактична зупинка, MQTT/TLS reconnect і свіжі дані |
| Wi-Fi | Те саме при окремій втраті радіоканалу | Не перевірено; тест gateway його не замінює |
| Живлення ESP32 | SU600 сам зупиняється; після reboot STOP і ARM=0 | Прийнято один цикл: E485/16, фізична зупинка, `restart_recovery`, свіжі 0 Гц/RUN «Ні»/ARM=0; затримку не виміряно |
| `DISARM` | Сеанс закінчений, RUN зупиняється; START заблокований | Прийнято зупинку, `local_disarm`, ARM=0 та блокування UI; надсилання START в обхід UI фізично не тестували |

Окремо відкритий випадок Offline після відсутності користувача, усунутий
перепідключенням ESP32: причину до reset не зафіксовано. Наприкінці тесту
живлення VFD залишився з помилкою 16 і вимкненим ARM; скидання помилки не зафіксоване.

Не від'єднувати силові проводи/RS485 вручну під напругою. Відмову RS485 готують
знеструмлено або відповідним тестовим роз'єднувачем фахівцем. TTL, дублікати,
переповнення таймера й збої пам'яті перевіряються також автоматичними тестами;
навмисне заклинювання, коротке замикання чи перевантаження не потрібні.

`CONTROL: last_stop=...` і `TEST: session=...` пояснюють місцеву зупинку.
Вона не створює вигаданої вебкоманди в журналі: причина поки доступна у Serial.
RUN означає стан VFD, а не датчик вала/потоку. Перевіряються реалізовані START,
STOP, частота, показання, графіки, журнал, сесії та зв'язок. Реверс, скидання
аварій, автоналаштування мотора, датчики та 4G цим режимом не додаються.

Повернення в читання: обидва прапорці firmware `false`, завантаження без
стирання NVS та `python -m app.bench.su600 --disable-control` через той самий `docker compose exec`.
