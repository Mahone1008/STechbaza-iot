# Керування V3 без повторного Serial ARM

Firmware **0.8.1**, ESP32-S3 N16R8 / SUSWE SU600, backend **0.50.0**, schema **0027**. Для вже налаштованого стенда `KERUMO-V3-SU600-001`. Це окремий режим дозволу керування; постійний пароль сайту, ролі та Authenticator не змінюються.

## Оновлення з 0.8.0

У 0.8.0 функція часу отримувала відсутній JSON member як `JsonVariant`; ArduinoJson 7 не створював `sent_at`. Після додавання `command_sequence_floor` сервер правильно відхиляв пакет без UTC часу з `invalid_envelope`. Firmware **0.8.1** створює поле прямим присвоєнням для telemetry, ACK і result. За відсутності синхронізованого часу передає явний `null`, без command cursor.

Якщо backend вже має поле `command_sequence_floor`, сервер і дані повторно змінювати не потрібно. Оновіть репозиторій через `git pull --ff-only origin main`, перевірте версію `0.8.1` у скетчі й завантажте його з наявним `config.local.h`. Збережіть усі credentials та три ввімкнені прапорці режиму. `Erase All Flash Before Sketch Upload` має залишитися Disabled. Після MQTT reconnect перевірте свіжі показання, `armed=1`, STOP та новий пуск із сайту.

CI перевіряє JSON, створений спільним firmware helper, фактичними backend моделями telemetry/ACK/result: UTC із command cursor, час після 2038 року та запуск до синхронізації годинника.

## Як працює

`KERUMO_ENABLE_REMOTE_OPERATION` зберігається в прошивці. Після ввімкнення живлення або відновлення мережі контролер сам перевіряє умови керування. Arduino IDE і повторна команда `ARM SU600 TEST` для звичайних пусків більше не потрібні. Читання, дозвіл керування і пуск двигуна залишаються окремими діями.

- Дозвіл з'являється лише при актуальному MQTT-зв'язку, синхронізованому часі, справному журналі, підтвердженому обладнанні, придатному extended-профілі SU600, відсутності помилки, STOP і виході 0 Гц.
- Сам дозвіл не записує START або частоту у VFD. Потрібна нова команда з сайту; штатний STOP залишає дозвіл для наступного пуску.
- Втрата мережі/RS485, помилка, невірний профіль або невідомий результат запускають захисну зупинку. Дозвіл може повернутися тільки після усунення причини й підтвердженого STOP. Firmware не скидає помилки частотника.
- Після перезавантаження старий намір RUN/незавершена програма спочатку зупиняється за журналом. Двигун, етапи та старий запуск розкладу не поновлюються. Дублікати відтворюють лише збережену відповідь; команди, створені до нового автоматичного дозволу, відхиляються.
- Локальний `DISARM` має пріоритет і блокує автоматичний дозвіл до успішного явного ARM або наступного boot. Після нового boot усі перевірки проходять заново; двигун не запускається. Для тривалого вимкнення режиму поверніть прапорець remote operation у `false` і завантажте скетч.
- Зміна обладнання/manifest не обходить локального підтвердження зупиненого обладнання. Factory provisioning і `BIND EQUIPMENT STOPPED` працюють за [своїм порядком](stage2-acceptance.md).

За замовчуванням режим вимкнений. Без нього зберігається ручний ARM. Обмеження extended-профілю, частоти й параметри моторного захисту ті самі, що у [підготовці SU600 з двигуном](v3-su600-extended-test.md). Профіль одного SU600 не підтверджує сумісність інших частотників.

## Увімкнути на вже підготовленому стенді

1. Зупиніть двигун. Оновіть репозиторій через `git pull --ff-only`, потім перебудуйте й перезапустіть обидва API **без очищення**:

   ```powershell
   Set-Location 'C:\Users\seraf\Documents\TechBaza\techbaza-iot'
   git pull --ff-only
   if ($LASTEXITCODE -ne 0) { throw 'Repository update failed.' }
   powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-staff-demo.ps1
   if ($LASTEXITCODE -ne 0) { throw 'API startup failed.' }
   ```

   Backend потрібно оновити **до** завантаження firmware 0.8.1: у MQTT-телеметрії з’явився необов’язковий `command_sequence_floor`. Сервер піднімає свій лічильник до збереженого в ESP32 лише зі свіжого прийнятого пакета цього пристрою; ніколи не зменшує його. Старі firmware без поля підтримуються. Це службова metadata, не новий показник у клієнтській панелі. Якщо після очищення прикладів картки V3 немає, спочатку [поверніть її до організації owner](v3-restore-after-reset.md) та перевірте свіжі показання у режимі читання. `-ResetExisting` для цього не потрібний.
2. Відкрийте **наявний** `firmware/kerumo_v3/config.local.h`. Замініть відповідні визначення; для кожного імені має бути один рядок:

   ```cpp
   #define KERUMO_ENABLE_CONTROL true
   #define KERUMO_ENABLE_EXTENDED_TEST true
   #define KERUMO_ENABLE_REMOTE_OPERATION true
   ```

   Wi-Fi, UID, MQTT credentials, CA й обладнання залиште чинними. Редагування лише `config.example.h` не змінює наявного local-файлу. Комбінація remote без CONTROL або EXTENDED_TEST не компілюється.
3. В Arduino IDE відкрийте `firmware/kerumo_v3/kerumo_v3.ino` і завантажте через USB. ESP32 core **3.3.1**, ArduinoJson **7.4.2**, ArduinoMqttClient **0.1.8**. Плата ESP32S3 Dev Module, Flash 16 MB, PSRAM OPI, Partition Scheme 16M Flash (3MB APP/9.9MB FATFS). **Erase All Flash Before Sketch Upload: Disabled**. USB CDC On Boot: Disabled для попереднього USB-UART; Enabled тільки для native USB. Збережіть попередній COM-порт/тип USB.
4. Serial Monitor на 115200 потрібний лише для перевірки: версія `0.8.1`, `storage=OK`, `mode=REMOTE / CHECKING`, `MQTT CONNECTED`, згодом `armed=1`. Якщо `armed=0`, перевірте зв'язок, час, STOP/0 Гц, помилки й параметри SU600. Успішне завантаження скетчу саме по собі не підтверджує дозвіл. Команду ARM вводити не потрібно.
5. Поверніть серверні можливості керування, програм і розкладів. У PowerShell із кореня репозиторію, коли клієнтський backend працює:

   ```powershell
   & {
       $ErrorActionPreference = 'Stop'
       Set-Location 'C:\Users\seraf\Documents\TechBaza\techbaza-iot'
       $dc = @('compose', '-p', 'techbaza-demo', '--env-file', '.env.demo', '-f', 'compose.demo.yml')
       foreach ($overlay in @('v3', 'controllers', 'staff')) {
           if (Test-Path ".env.$overlay") {
               $composeFile = "compose.$overlay.yml"
               if ($overlay -eq 'staff') { $composeFile = 'compose.staff.demo.yml' }
               $dc += @('--env-file', ".env.$overlay", '-f', $composeFile)
           }
       }
       & docker @dc exec -T backend python -m app.bench.su600 --enable-control-extended-test
       if ($LASTEXITCODE -ne 0) { throw 'V3 control configuration failed.' }
   }
   ```

   Очікуються `control_enabled: true`, `test_session: extended`. Команда не прошиває ESP32 і не запускає двигун; вона змінює тільки серверну конфігурацію цього стенда. Членства/паролі/історія інших акаунтів зберігаються.
6. Відкрийте <http://127.0.0.1:3000/login>, увійдіть `owner@kerumo-demo.example.com`, виберіть «DEMO: клієнт A», об'єкт V3 і контролер SU600. Оновіть панель, дочекайтеся свіжої діагностики й «Дозвіл керування: Так». Виберіть допустиму частоту, потім натисніть пуск. Після STOP наступний пуск також виконується з сайту. Завершене налаштування працює із закритим Arduino IDE, поки контролер має живлення й сервер/gateway доступні.

## Перевірка на стенді

Програмні тести й компіляція перевіряють реалізацію. Фізичне приймання **0.8.1** ще потрібне на конкретній установці; попередні досьє ARM не підтверджують новий режим.

| Перевірка | Очікуваний результат |
|---|---|
| Повернення картки після reset | Свіжа телеметрія відновлює серверний лічильник; нова команда не відхиляється як стара; NVS не очищується |
| Завантаження, IDE закрита | Свіжі показання та дозвіл без Serial ARM; двигун зупинений |
| Пуск, понад 60 с, STOP, повторний пуск | Нові команди виконуються; STOP підтверджений; повторний ARM не потрібний |
| Втрата gateway під час RUN | Зупинка; під час втрати немає дозволу |
| Повернення gateway | Після підтвердженого STOP і перевірок дозвіл повертається; двигун не запускається до нової команди |
| Помилка VFD або втрата RS485 | Зупинка/блокування; дозвіл повертається після усунення причини, без автоматичного пуску |
| Перезавантаження ESP32 під час RUN/програми | Відновлення STOP з журналу; програма/двигун не продовжуються; нова команда потрібна |
| Локальний DISARM | STOP і відсутність дозволу, навіть після очікування/повернення мережі в цьому boot |

Фіксуйте firmware version, фактичну зупинку, новий пуск лише після натискання, помилки VFD і час реакції. Дозвіл на екрані та STOP/readback VFD не є незалежним вимірюванням обертання вала. Для остаточного приймання використовуйте також чинні перевірки проводки, захисту мотора й незалежної зупинки з інструкції стенда.
