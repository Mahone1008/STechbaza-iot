# Аудит інтерфейсу режимів керування — 01.10.2026

Обсяг: блок керування пристроєм, звичайний режим, таймер, етапи,
календар, їхні переходи, запити й права доступу. Початкова ревізія —
`46c5925`. Підстава: три скріншоти оператора від 01.10.2026
(`image(20261001-144838).png`, `image(20261001-144941).png`,
`image(20261001-145019).png`). Це перевірка інтерфейсу, не нове фізичне
приймання firmware, V4/V5 або всієї production-системи.

## Знайдені причини та виправлення

| Проблема | Причина | Поточна поведінка |
|---|---|---|
| Постійний блок «Розклади пристрою» | Окреме `schedulesOpen` у сторінці, незалежне від режиму | Календар належить вибраному режиму всередині налаштувань |
| «Календар і збережені правила — нижче» після згортання | Посилання було поза `details` | Посилання й дубльований перемикач видалено; згортання приховує весь календар |
| Підказка етапів у таймері | Спільний текст для двох режимів | Окремі пояснення тривалості та автоматичної зупинки |
| Порожній таймер мав кнопку запуску етапів | Назва залежала від валідності плану | Назва відповідає режиму навіть за невалідних полів |
| Значення таймера змінювали перший етап | Спільний масив чернетки | Незалежні чернетки таймера й етапів |
| Перевантажений календар | Список, редактор і стороння історія одночасно | Список або редактор; окремі групи запуску/зупинки, згорнуті додаткові поля |
| Місяці роботи для разового запуску | Сезонні фільтри показувалися завжди | Місяці тільки для повторень; повернення до разового режиму скидає цей фільтр |
| Підказка ставала частиною назви поля для assistive technology | `label` включав текст hint | `aria-labelledby` вказує на назву, `aria-describedby` — на пояснення |

Редактор перевіряє обов'язкові базові поля та межі чисел засобами HTML
перед preview. Серверний preview і явне підтвердження залишаються
обов'язковими для збереження та ввімкнення. Зміна полів скидає preview.
Після помилки оновлення списку є пояснення та повторне читання, зокрема
під час редагування.

## Володіння станом і витрати

`CommandControls` володіє вибраним режимом і станом згортання.
`ProgramSettings` відповідає лише за поля таймера/етапів. Сторінка
пристрою більше не керує окремим відкриттям календаря.

Календар завантажується динамічно після вибору режиму. Згортання зберігає
чернетку, але вимикає polling списку та прибирає активне читання історії.
Перехід в інший режим закриває календар без автоматичного запису.
Самі збережені правила та прийнятий контролером запуск від цього не
змінюються. Наявні browser visibility, session та backoff guards збережені.
Нових залежностей застосунку немає.

Читач із `command.read` має календар лише для перегляду. Під час виконання
плану можна переглядати майбутні розклади; новий запуск таймера/етапів
залишається заблокованим, STOP доступний за чинними правами. Незбережена
форма не відновлює START після F5. Збережений активний план, як раніше,
читається за ID команди з телеметрії.

## Перевірки та межі

Сценарії браузера охоплюють перемикання всіх режимів, згортання/повторне
відкриття, збереження чернетки під час згортання, припинення polling,
незалежні поля таймера/етапів, підтвердження без дублювання, скидання
preview після редагування, конфлікти, F5, viewer, відсутню capability,
STOP під час активного плану та ширини 320/393/1280 px.

## Повторний аудит після оновлення до 0.43.0 / 0.5.0

Початкова ревізія — `30c05d2`. Скриншоти оператора `155218`–`155308`
підтверджують оновлення backend до 0.43.0 та запуск frontend, `155426` —
firmware 0.5.0 і MQTT/TLS. Це не доказ виконання календарного запуску.
Скріншоти `155616`–`155704` показують порядок TTL/режиму, системні вікна
автооновлення й часу та збережене повідомлення про попередню команду.

| Спостереження | Причина та виправлення |
|---|---|
| TTL після режиму та відсутній у календарі | Поле перенесено перед режимом і показано в усіх режимах оператора; у календарі пояснено різницю між TTL кнопкових команд і фіксованим вікном старту 30 с |
| Пояснення сприймалося як текст іншого режиму | Чинні описи таймера/етапів на цих знімках відповідали режимам, але стояли після TTL; тепер кожен із чотирьох режимів має власний `aria-describedby` безпосередньо під вибором |
| Попередня команда залишалась під новим режимом | Звичайне повідомлення форми очищується при перемиканні; окрема картка пояснює, що показує вибрану команду з журналу. Її стан та невизначений результат не скидаються |
| Велика рамка «Автооновлення» на мобільному екрані | Це поле не входило до чинних стилів обмеженого select; тепер використовує спільний `SelectField` і той самий picker у підтримуваних браузерах |
| Системний picker часу виходив за екран | Один `TimeField` для початку, зупинки та змін частоти: цифрова клавіатура, ГГ:ХХ, перетворення 4 цифр, перевірка обов'язковості й діапазону |
| «Лише вручну» не зупиняло календар | Спільний вибір інтервалу передається списку розкладів та історії; історія має окрему ручну кнопку |
| «Щохвилини», але команди опитувались кожні 5 с | Журнал і вибрана команда тепер отримують сам інтервал замість boolean auto |

Немає нових JavaScript-залежностей або зміни API/firmware. Окремий компонент
часу прибирає три копії поведінки полів; тексти режимів зібрані в одному
типізованому словнику. Чернетки таймера/етапів, guards команд, STOP,
підтвердження й серверний preview збережені.

Витрати обмежені архітектурно: план до 8 етапів виконується локально,
браузер не надсилає команду щосекунди. Календар використовує спільний
worker команд (типово раз на 2 с), індекс `next_check_at` та обмежену
партію до 100 правил; майбутні роки не матеріалізуються в пам'яті.
На відкритій панелі вибір 60 с зменшує частоту журналу/стану команди з
12 до 1 запиту за хвилину на відповідний блок. Прихований календар,
hidden/offline та ручний режим не створюють періодичних читань цих блоків.
Це перевірка коду й кількості запитів, не вимірювання енергоспоживання,
CPU/RAM під fleet-навантаженням чи закриття SCHEDULE-01.

Для вже оновленого стенда 0.43.0/0.5.0 достатньо зупинити dev-сервер
frontend через Ctrl+C, виконати Windows-команди вище та оновити сторінку.
