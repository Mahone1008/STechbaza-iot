## Знайдені причини та виправлення

| Проблема | Причина | Поточна поведінка |
|---|---|---|
| Постійний блок «Розклади пристрою» | Окреме `schedulesOpen` у сторінці, незалежне від режиму | Календар належить вибраному режиму всередині налаштувань |
| «Календар і збережені правила — нижче» після згортання | Посилання було поза `details` | Посилання й дубльований перемикач видалено; згортання приховує весь календар |
| Підказка етапів у таймері | Спільний текст для двох режимів | Окремі пояснення тривалості та автоматичної зупинки |
| Порожній таймер мав кнопку запуску етапів | Назва залежала від валідності плану | Назва відповідає режиму навіть за невалідних полів |
| Значення таймера змінювали перший етап | Спільний масив чернетки | Незалежні чернетки таймера й етапів |
| Перевантажений календар | Список, редактор і стороння історія одночасно | Список або редактор; окремі групи запуску/зупинки, згорнуті додаткові поля |
| Місяці роботи для разового запуску | Сезонні фільтри показувалися завжди | Місяці тільки для повторень; повернення до разового режиму скидає цей фільтр |
| Підказка ставала частиною назви поля для assistive technology | `label` включав текст hint | `aria-labelledby` вказує на назву, `aria-describedby` — на пояснення |

Редактор перевіряє обов'язкові базові поля та межі чисел засобами HTML
перед preview. Серверний preview і явне підтвердження залишаються
обов'язковими для збереження та ввімкнення. Зміна полів скидає preview.
Після помилки оновлення списку є пояснення та повторне читання, зокрема
під час редагування.

## Володіння станом і витрати

`CommandControls` володіє вибраним режимом і станом згортання.
`ProgramSettings` відповідає лише за поля таймера/етапів. Сторінка
пристрою більше не керує окремим відкриттям календаря.

Календар завантажується динамічно після вибору режиму. Згортання зберігає
чернетку, але вимикає polling списку та прибирає активне читання історії.
Перехід в інший режим закриває календар без автоматичного запису.
Самі збережені правила та прийнятий контролером запуск від цього не
змінюються. Наявні browser visibility, session та backoff guards збережені.
Нових залежностей застосунку немає.

Читач із `command.read` має календар лише для перегляду. Під час виконання
плану можна переглядати майбутні розклади; новий запуск таймера/етапів
залишається заблокованим, STOP доступний за чинними правами. Незбережена
форма не відновлює START після F5. Збережений активний план, як раніше,
читається за ID команди з телеметрії.

## Перевірки та межі

Сценарії браузера охоплюють перемикання всіх режимів, згортання/повторне
відкриття, збереження чернетки під час згортання, припинення polling,
незалежні поля таймера/етапів, підтвердження без дублювання, скидання
preview після редагування, конфлікти, F5, viewer, відсутню capability,
STOP під час активного плану та ширини 320/393/1280 px.

У локальному контейнері стандартний browser download повертав пошкоджений

без зміни залежностей застосунку, тестових сценаріїв, retries або таймаутів.
GitHub CI використовує штатну конфігурацію проєкту. Наведені числа —
локальний прогін; історичні CI counts у досьє календаря тут не зараховані.
SCHEDULE-01 і незавершені фізичні сценарії PROGRAM-01 залишаються відкритими.
