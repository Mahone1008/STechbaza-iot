# Досьє V3 — читання SU600 на фізичному стенді та відображення на сайті

Дата фіксації: **30.09.2026**. Перевірки виконані користувачем 29–30.09.2026.
Час подій нижче — **Europe/Kyiv (UTC+03:00)**.

**Статус: базове наскрізне читання прийнято в перевіреному режимі STOP.
Перевірки відмов виконано частково. Фізичне керування ще не прийнято.**

Підстава — надані користувачем скриншоти Serial Monitor, сайту й PowerShell,
а також його підтвердження звіряння показань. Це запис фізичного приймання;
успіх автоматичних тестів сам по собі не закриває відкриті пункти нижче.

## 1. Стенд і межі приймання

- Частотник SU600, ESP32-S3 N16R8, ізольований UART–RS485.
- UART: RX GPIO18, TX GPIO17, 9600 baud, 8N1, Modbus slave 1.
- Локальний Wi-Fi, MQTT через TLS gateway, backend і сайт на Windows ПК.
- Firmware: **0.1.0**; backend у відповіді `/health`: **0.39.0**.
- Режим: `KERUMO_ENABLE_CONTROL false`, Serial `READ ONLY`, дозвіл `armed=0`.
- Сценарій приймання: частотник у STOP, без підключеного двигуна.
- UID: `KERUMO-V3-SU600-001`.
- Організація: **DEMO: клієнт A**.
- Об’єкт: **V3 — фізичний стенд SU600**.
- Пристрій: **V3 — реальний SU600 / ESP32-S3**.

Цей UID відокремлено від симулятора. Наявність зв’язку, стан частотника й
актуальність вимірювань перевірялися окремо. Читання в STOP не підтверджує
точність вимірювань у всьому діапазоні, роботу двигуна або подачу води.

Інструкція: [підготовка та запуск V3](v3-su600-bench.md).
Реалізацію при складанні запису звірено з revision
`ab2dd5dd63f8f9d3b98b21d8175e63fb8110491a`; запис не є вимірюванням
хешу завантаженого на ESP32 бінарного файлу.

## 2. Підтверджене читання

У Serial Monitor отримано:

```text
SU600: read=1 profile=1 config=1
F0.02=2 F0.03=6 F0.04=500 F0.05=500 F0.06=0
F6.00=1 F6.01=0 F6.02=0 F6.03=5 F6.04=100 F6.05=0 armed=0
READ: fault=OK:0 state=OK:1290 set=OK:0.00 out=OK:0.00 I=OK:0.0 U=OK:0.0
```

Це сирі значення параметрів у форматі прошивки; наприклад, `F0.04=500`
відповідає 50.0 Hz у цьому профілі. Код стану збережено як отримано;
на сайті стан RUN показано як «Ні».

| Показник | Спостережений результат |
|---|---|
| Задана частота | 0 Hz |
| Вихідна частота | 0 Hz |
| Струм | 0 A |
| Вихідна напруга | 0 V |
| Стан RUN частотника | Ні |
| Код помилки | 0, регістр успішно прочитано |
| Зв’язок із частотником | Так |
| Налаштування профілю перевірено | Так |
| Локальний дозвіл керування | Ні |

Користувач підтвердив збіг показань сайту, Serial Monitor і панелі SU600.
На сайті для фізичного UID спостерігалися Online і «Свіжі дані».
Порожній перелік дозволених команд відповідає режиму читання.

заборона Modbus write реалізована в коді.

## 4. Виявлені проблеми середовища

### 4.1. Локальна адреса та browser session

Інструкція й повідомлення сценарію підготовки спочатку відкривали сайт через
`localhost:3000`, тоді як API було налаштовано на `127.0.0.1:8001`.
Таке поєднання несумісне з очікуваною роботою refresh cookie `SameSite=Strict`.

Користувач спостерігав повернення на login після F5 та приблизно під час
першого оновлення access token. Точний HTTP-відгук початкової невдалої спроби
не зафіксований, тому причина саме того виходу є обґрунтованим поясненням,
а не окремо записаним мережевим доказом.

Після використання `http://127.0.0.1:3000` показано успішні `refresh → 200`,
`me → 200` і «Сесія відновлена». У локальному конфігу підтверджено:

```text
NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8001
```

Посилання виправлено в commit
[`ab2dd5d`](https://github.com/Mahone1008/STechbaza-iot/commit/ab2dd5dd63f8f9d3b98b21d8175e63fb8110491a).
Довготривалу безперервну browser session цими скриншотами не прийнято.

### 4.2. API відповідав у контейнері, але був недоступний із Windows

Зафіксовано:

- backend мав статус `healthy`;
- `docker port` показував `8000/tcp -> 127.0.0.1:8001`;
- HTTP-запит усередині контейнера повертав `status: ok`;
- прямий запит із Windows через `curl.exe --noproxy "*"` завершувався
  `curl: (52) Empty reply from server`;
- сайт показував «Не вдалося перевірити сесію» з повідомленням про недоступний backend.

Після звичайного **Restart Docker Desktop** отримано:

```text
HTTP/1.1 200 OK
date: Wed, 30 Sep 2026 06:17:03 GMT
{"status":"ok","service":"techbaza-backend","version":"0.39.0"}
```

Підтверджено відновлення доступу Windows → опублікований порт API.
Точна внутрішня причина збою Docker/мережі хоста не встановлена.
Успішний `/health` не підтверджує доставку телеметрії від ESP32.

У цей період Serial показував `MQTT: reconnect failed (-2)`, водночас
читання SU600 лишалось успішним. Сам цей код не доводить помилку пароля
або сертифіката. Користувач також повідомив про переключення живлення ESP32
з окремого блока 5 V на USB ПК; такий перезапуск не можна зарахувати як
відновлення MQTT без перезавантаження контролера.

## 6. Наступний крок

Спочатку в поточному READ ONLY підтвердити `MQTT CONNECTED / TLS`,
Online і свіжі дані після відновлення Docker. Далі завершити окремі перевірки:

1. Зупинка та запуск лише gateway при незмінному живленні ESP32:
   Offline/стара телеметрія → Online/нові дані, без нового перезапуску плати;
   HTTP API і browser session мають лишатися доступними.
2. Відсутність RS485, підготована при знеструмленому стенді:
   контролер Online, `vfd_link=false`, вимірювання частотника недоступні;
   потім перевірене відновлення читання. Проводку не змінюють під напругою.

Наступний етап керування — **обмежений стендовий тест SU600 без двигуна**:
задати 10 Hz → звірити задану частоту → START → прочитати RUN → STOP →
підтвердити STOP і вихідні 0 Hz. ACK доставки й підтверджений фізичний
результат команди оцінюють окремо. Окремо залишаються приймання TTL,
блокувань профілю/часу, повторних команд і поведінки при втраті зв’язку.

Для цього етапу існують три окремі умови дозволу: збірка прошивки з керуванням,
capability фізичного пристрою на backend і локальний `ARM SU600`.
Цей документаційний запис жодну з них не вмикає.

Тест не є «повним керуванням» усіма параметрами частотника: reverse, jog,
reset fault і записи F0/F6 не входять до реалізації. Сумісність із SU800,
SU900 та іншими виробниками цим стендом не підтверджується.

Навіть без двигуна виходи U/V/W під RUN можуть бути під небезпечною напругою.
Програмний Auto-STOP не замінює апаратного аварійного захисту. Вимкнена ESP32
не може надіслати STOP — поведінка установки при втраті її живлення
потребує окремого рішення перед підключенням двигуна/насоса.

**Підсумок приймання: базове читання фізичного V3 підтверджене.
Керування, повне приймання відмов та готовність до роботи з насосом залишаються відкритими.**
