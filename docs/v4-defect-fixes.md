# Виправлення дефектів V4 — 13.10.2026

Backend **0.55.1**, firmware **0.12.1**; схема БД залишається **0031**.
Зміни доповнюють [заводський Full onboarding](v4-full-control-onboarding.md).
Самостійний майстер власника, тимчасовий помічник та повний каталог F/P
залишаються окремим наступним етапом.

## Журнал і повторна ініціалізація

Повторний `Controller.begin()` спочатку блокує керування й запис журналу.
Помилка читання, CRC, UID або некоректна незавершена програма не можуть
залишити `storageOk=true`. Поки журнал не перевірено, наступний STOP або
спроба зберегти результат не перезаписують NVS порожнім журналом і не
відновлюють дозвіл. Коректний журнал зберігає watermark команд.

Якщо той самий Controller уже виконує команду або має відомий намір руху,
повторна ініціалізація відхиляється до читання NVS. Збережений у RAM намір
дозволяє завершити захисний STOP; нова ініціалізація можлива після його
завершення. Завантаження не відновлює RUN чи перервану програму.

## Втрата зв’язку під час перевірок

Читання Modbus та запис NVS можуть тривати довше за дозвіл зв’язку.
Прошивка повторно перевіряє чинний зв’язок після цих операцій перед
RUN, зміною частоти та відповідними кроками програм/календарних запусків.
Сервісний запис також повторно перевіряє дозвіл після збереження наміру.
При втраті дозволу новий керувальний запис не виконується; захисний STOP
залишається можливим. Нове підключення саме по собі не надсилає RUN.

## Ротація ключів і місцеве підтвердження

Ротація атомарно скасовує серверний дозвіл та створює нову immutable
ревізію наявної конфігурації. Паспорт, межі, module і binding не змінюються;
змінюються revision/hash. Тому навіть свіжа телеметрія старої конфігурації
більше не дозволяє commissioning. За відсутності конфігурації ротація
не створює вигаданий паспорт. Збій синхронізації з брокером залишає новий
намір ротації й вимогу підтвердження; worker може повторити синхронізацію.

Плата зберігає підтвердження для конкретних UID, hash конфігурації та
ревізії мережевого ключа. Незмінна трійка переживає reboot; зміна будь-якої
частини потребує нової місцевої перевірки. **Після оновлення з 0.12.0 старе
hash-only підтвердження також потребує одноразової місцевої перевірки**
за чинною процедурою. NVS і command watermark стирати не потрібно.
Підтвердження й повторний дозвіл використання не запускають двигун.

## Запрошення від службового адміністратора

Customer RLS приховує рядок staff user, тому звичайний `session.get(User)`
не знаходив автора запрошення й повертав 404. Перевірка використовує
наявну `customer_actor_metadata` лише для прихованого автора. Вона читає
чинні права без password hash, MFA, recovery чи session secrets.
SQL-політики й набір відкритих клієнту даних не розширено.

Прийняття повторно перевіряє активність і права автора, область та строк,
пошту одержувача, відкликання й одноразовість посилання. Тестові HTTP-запити
виконуються як `kerumo_customer` під справжніми PostgreSQL RLS-політиками.

## Регресійні перевірки

- `firmware/tests/core_test.cpp`: повторний begin на тому самому об’єкті,
  пошкодження журналу, відновлювальний STOP, втрата зв’язку під час
  Modbus/NVS для ручних команд і програм.
- `firmware/tests/equipment_test.h`: місцеве підтвердження за UID/hash/key revision.
- `backend/tests/test_controller_lifecycle_postgres.py`: старе підтвердження
  після ротації, новий manifest, повторна ротація та збій брокера.
- `backend/tests/test_invitation_rls_postgres.py`: перегляд, прийняття й
  реєстрація через запрошення з customer RLS; чинні права та приватність staff.

Повний backend gate запускається через `python -m app.tools.backend_check`
з `TECHBAZA_RUN_DB_TESTS=1`, `TECHBAZA_RUN_MQTT_TESTS=1` та окремими
PostgreSQL/MQTT. Staff suite запускається окремо з `APP_PLANE=staff`.
Native firmware перевіряється з AddressSanitizer/UndefinedBehaviorSanitizer;
ESP32 збирається pinned toolchain із V3/V4 workflows.
Ці перевірки не замінюють [фізичного приймання V4](v4-full-control-onboarding.md).
